# Потребности пользователей

[[Навигация сервиса]] · [[Правила модели]]

Требования сгруппированы по смыслу и расположены по ходу работы с заявкой. В каждой группе одна таблица со строками-разделителями по приоритетам MoSCoW. Заголовок и описание группы задают общий контекст для ее требований.

В матрицу включены атомарные требования с конкретной бизнес-ценностью: сокращение ручной работы и затрат, соблюдение сроков, предотвращение невыполнимых назначений или сокращение числа необслуженных заявок. Для информационных требований указано, какое рабочее решение позволяет принять информация. Польза описывает ожидаемый эффект, а не подтвержденный результат внедрения.

Приоритеты: **Must have** - обязательные, **Should have** - важные дополнительные, **Could have** - при наличии времени.

## Маршруты инженеров

Отображение и объяснение маршрутов.

Таблица 4. Маршруты инженеров

| Как | Я хочу | Чтобы |
|---|---|---|
| **Must have** |  | |
| диспетчер | видеть маршруты инженеров на карте           | выявить лишние перемещения до выдачи плана      |
| диспетчер | получать понятное объяснение выбора маршрута | выявить ограничения, мешающие сократить маршрут |

Точки заявок на карте - деталь отображения маршрутов, предусмотренная ТЗ. Они не выделены в самостоятельную потребность: подбор близких заявок для одного инженера выполняет алгоритм автоматического распределения.

Маршрут начинается в стартовой точке инженера. Для обязательного прототипа возврат после последней заявки не требуется. ТЗ не требует доказательства математического оптимума.

## Плановые показатели

Число задействованных инженеров, пробег и сравнение планов.

Таблица 5. Плановые показатели

| Как | Я хочу | Чтобы |
|---|---|---|
| **Must have** | Рассчитанный и базовый планы сравниваются на одинаковых исходных данных. | |
| диспетчер | видеть число задействованных инженеров | выделить необходимое число сотрудников на выполнение плана |
| диспетчер | видеть пробег каждого инженера         | определить маршруты с наибольшим пробегом для проверки     |
| диспетчер | видеть суммарный пробег плана          | оценить затраты на перемещения по всему плану              |
| диспетчер | сравнивать число задействованных инженеров | оценить экономию персонала при том же объеме работ        |
| диспетчер | сравнивать пробег каждого инженера         | выявить увеличение пробега отдельных инженеров            |
| **Should have** | Выбор между несколькими вариантами плана. | |
| диспетчер | сравнивать несколько вариантов плана по выбранной метрике | выбрать менее затратный план при сопоставимом объеме работ |
| **Could have** | Дополнительные критерии: число выполнимых заявок и время в пути. | |
| диспетчер | сравнивать число выполнимых заявок при нехватке ресурсов | выбрать план с меньшим числом необслуженных заявок |
| диспетчер | сравнивать время в пути | высвободить больше рабочего времени для выполнения заявок |

Базовый вариант из ТЗ: заявки идут по порядку поступления и назначаются первому по порядку во входных данных доступному инженеру, удовлетворяющему ограничениям. Порядок посещения совпадает с порядком назначения. При сравнении также нужно учитывать неназначенные заявки: уменьшение числа исполнителей за счет невыполненных работ само по себе не подтверждает улучшение плана.

## Перераспределение заявок

Корректировка назначений при изменении заявок или доступности инженеров.

Таблица 6. Перераспределение заявок

| Как | Я хочу | Чтобы |
|---|---|---|
| **Must have** |  | |
| диспетчер | перестраивать план при поступлении срочной заявки | оперативно включить срочную работу в расписание                 |
| диспетчер | учитывать повышенный приоритет срочной заявки     | обслужить срочные заявки в первую очередь при нехватке ресурсов |
| **Should have** |  | |
| диспетчер | вручную переназначать заявку другому инженеру | учесть обстоятельства, отсутствующие в системе   |
| диспетчер | перестраивать план при отмене заявки          | освободить время инженера для действующих заявок |
| диспетчер | перестраивать план при недоступности инженера | сократить число заявок без исполнителя           |

Для обязательного перепланирования предложен сценарий «поступила срочная заявка». ТЗ допускает выбрать вместо него отмену заявки или недоступность инженера. Реализация всех трех событий для Must have не требуется.

## Основания приоритетов

Потребности Should have помогают диспетчеру управлять рабочим днем после реализации обязательного сценария.

Потребности Could have улучшают качество решений, но не нужны для завершения обязательной демонстрации.
