# Параметры расчета

## Параметры сервиса

### Планирование

| Поле | Название | Тип | Обязательность | Источник | Комментарий |
|---|---|---|---|---|---|
| `timezone` | Часовой пояс планов | Строка IANA | Да | Пользователь: выбирает часовой пояс в настройках |  |
| `objective_order` | Порядок критериев | Список кодов | До расчета | Пользователь: задает согласованный порядок критериев | Конкретный порядок еще требует подтверждения |
| `search_time_limit_seconds` | Лимит поиска | Целое, секунды | До расчета | Пользователь: задает лимит расчета после замеров | Больше нуля |

### Маршрутный API

| Поле | Название | Тип | Обязательность | Источник | Комментарий |
|---|---|---|---|---|---|
| `routing.provider` | Поставщик маршрутов | Строка | До расчета | Пользователь: выбирает поставщика маршрутного API | Поставщик пока не выбран |
| `routing.base_url` | Адрес API | URL | До расчета | Пользователь: указывает адрес из документации выбранного поставщика |  |
| `routing.credential_ref` | Ссылка на ключ доступа | Строка | Если API требует ключ | Автоматически: система сохраняет ссылку на ключ, введенный пользователем при подключении | Сам ключ в заметках не хранится |
| `routing.transport_profiles` | Соответствие профилей транспорта | Объект: способ → код API | До расчета | Автоматически: представление соответствий из «Способ передвижения.routing_profile»; редактирование в справочнике способов передвижения | Для используемых способов: car, walking, bicycle, public_transport |
| `routing.supports_departure_time` | Учет времени отправления | Логический | До расчета | Пользователь: указывает подтвержденную документацией возможность выбранного API |  |

### Координаты адресов

| Поле | Название | Тип | Обязательность | Источник | Комментарий |
|---|---|---|---|---|---|
| `geocoding.provider` | Сервис геокодирования | Строка | Если адреса преобразуются автоматически | Пользователь: выбирает сервис преобразования адресов в координаты | Может совпадать с маршрутным сервисом, выбор еще не сделан |

## Правила расчета

- Предлагаемый порядок: urgent_unassigned, unassigned, used_engineers, distance_km. Он дает срочным заявкам преимущество при дефиците ресурсов и еще требует подтверждения.
- Базовый алгоритм берет заявки в порядке поступления и назначает первому подходящему сотруднику по порядку входа. Заявки маршрута следуют порядку назначения.
- Истечение лимита поиска не доказывает невозможность решения.

## Получение маршрутов и статусов

- Алгоритм отправляет маршрутному API пары координат, способ передвижения и, если поддерживается, время отправления. Участки проверяются на плановое время; время туда и обратно может различаться.
- Отсутствие маршрута и ошибка API различаются; ошибка не заменяется нулевым временем.
- Для источника статусов нужно определить способ получения, ключ заявки, время факта, словарь статусов и обработку повторных или запоздавших сообщений. Ручной режим для демо остается вариантом. Параметры webhook, опроса и доступа уточняются после выбора источника.
