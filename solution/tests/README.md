# Тесты планировщика `planner`

Сьют написан **строго по `solution/SPEC.md`**: имена классов, полей и функций берутся
оттуда буква в букву. Тесты не подстраиваются под реализацию — расхождение между SPEC и
кодом должно быть видно как красный тест, а не спрятано.

## Как запускать

Из корня репозитория (`E:\Programming\ЛЦТ 2026`):

```bash
python -m pytest solution/tests -q            # весь сьют
python -m pytest solution/tests -q -m "not slow"   # быстрый прогон (без нагрузочных)
python -m pytest solution/tests/test_replan.py -v  # один файл
python -m pytest solution/tests -q -m property     # только property-style прогоны
```

`conftest.py` сам добавляет `solution/` в `sys.path`, отдельной установки пакета не нужно.
Конфигурация лежит в `solution/tests/pytest.ini` — корень репозитория не затрагивается.

Маркеры: `slow` (дольше ~1 с), `property` (псевдослучайные сценарии), `realdata` (чтение CSV
из каталога `Обезличивание`). Внешних зависимостей, кроме `pytest`, нет.

## Инфраструктура

| файл | назначение |
|---|---|
| `conftest.py` | `sys.path`, общие фикстуры (каталоги, таймзона, дата сценария) |
| `factories.py` | билдеры `eng`/`req`/`sc`/`event`, независимые «оракулы» (гаверсинус, время в пути, рабочий календарь), генератор псевдослучайных сценариев, утилиты доступа к результату |
| `pytest.ini` | регистрация маркеров, `--strict-markers` |

`factories.py` терпимо резолвит публичные имена из `planner`, `planner.enums`, `planner.models`,
`planner.result`, `planner.calendar`, `planner.travel`, `planner.feasibility`, `planner.cost`.
Если пакет отсутствует или в нём нет нужного имени — тест-модуль **скипается** с внятной
причиной, а не разваливает коллекцию.

Оракулы в `factories.py` (`oracle_haversine_km`, `oracle_travel_minutes`, `OracleCalendar`)
реализованы независимо от `planner`, чтобы формулы SPEC проверялись, а не повторялись.

Дефолты билдеров: дата **2026-08-17**, пояс **UTC+3**, время задаётся строками `"HH:MM"`.
`sc()` по умолчанию перенумеровывает `input_order` по позиции в списке — именно от него
зависит baseline и все tie-break'и.

## Что сьют нашёл и что из этого вышло

Первый прогон дал 6 падений; все шесть оказались настоящими расхождениями SPEC ↔ реализация
и были исправлены в `planner`, а спорные места — зафиксированы в SPEC:

| находка | решение |
|---|---|
| `contains(13:00)=True`, но `first_moment_at_or_after(13:00)=14:00` | границы интервала включительны **везде**: `contains`, `first_moment_at_or_after`, `add(t,0)`, `sub(t,0)` |
| `sub(t, 0)` в начале интервала возвращал `None` | обратимость `add`/`sub` восстановлена |
| `no_engineers` при непустом списке инженеров (все `active=False`) | статические проверки идут по всем инженерам входа; теперь `no_work_time` |
| после `CLIENT_REFUSAL` план не проходил `validate_plan` | ремонт валидируется против сценария из `apply_event()`, а не против исходного |
| `PlanDiff` объявлял изменённый маршрут неизменным | подпись маршрута в diff учитывает `service_end_at` |

### Ревью кода и документации

Второй заход — сверка кода с базой знаний и с реальными выгрузками. Пять расхождений,
на каждое добавлен регрессионный тест:

| находка | решение |
|---|---|
| ожидание у клиента списывалось в занятость: маршрут из четырёх заявок показывал 97 % загрузки при реально свободном дне | выезд откладывается до начала работ, свободное время видно как `Visit.idle_before_minutes` |
| допуск календаря (1e-9 мин) был мельче разрешения `datetime`, и round-trip «минуты → datetime → минуты» перепрыгивал через обед: 13:00 превращалось в 14:00 | допуск поднят до 1e-6 минуты — крупнее микросекунды, но незаметен для расписания |
| расписание пересчитывалось от начала смены целиком, поэтому исчезновение раннего визита сдвигало **начатые работы** в прошлое | locked-префикс переносится из прошлого плана как факт (`RouteState.adopt`), верификатор такие визиты не пересчитывает |
| `apply_event` не двигал границу снимка, и после события заявка попадала в маршрут, но выпадала из назначений и метрик | `as_of = max(as_of, event.at)`; верификатор проверяет, что у каждого визита есть `Assignment` |
| норматив брался по HD раньше, чем по BK: 126 строк из 413 реальных выгрузок получали чужую длительность («Нет линка» — 80 мин вместо 30) | разбор «точная пара → BK → HD → default»; вид работ и норматив только по BK, HD уточняет снаряжение |
| `ejection_depth` вытеснял ровно одну заявку при любом значении | вытеснение идёт по нарастающей до заданной глубины; при 2 авария освобождает два слота подряд |
| `ejection_depth = 1` по умолчанию: вытеснение вырождалось в «сними ровно одну заявку и сдайся», и авария на 80 минут в плотной смене не размещалась никогда | значение по умолчанию поднято до 3 — средняя ступень освобождает несколько слотов подряд |
| вытеснение было последней ступенью: если аварию не вмещал ни один маршрут по отдельности, она уходила в отказ, хотя вместе с остатком дня раскладывалась | добавлена третья ступень — пересчёт остатка дня поверх замороженных префиксов, с правилом приёмки по `quality_key()` и тай-брейком на число изменённых маршрутов |
| пул неразмещённых собирался до вставки аварии: заявка, которая уже числилась неназначенной и пришла событием, попадала в маршрут **дважды** (её ставила точечная вставка, а следом regret-вставка) | пул собирается после размещения аварии и фильтруется по уже назначенным; вытесненные на второй ступени заявки тоже попадают в regret-вставку |
| инженер, который выехал, но не доехал, считался свободным: пересчёт разворачивал его на другой адрес | заморозка идёт и по `departure_at < event.at`; исключение — инженер, выбывший по `ENGINEER_UNAVAILABLE`: его поездка прервана вместе со сменой |
| статус «работы завершены» позже плана не опровергал допущение о следующем визите: тот оставался «начатым по плану» и накладывался на работу, которая на самом деле ещё шла | факт обрывает замороженный префикс — визит, который не мог начаться, возвращается в расчёт и планируется от фактического времени |
| ремонт по событию назначал работу **задним числом**: при событии в 11:40 вытесненная заявка вставала на 09:00 инженеру, чей день начинался позже | у маршрута появился «пол» `RouteState.floor_m` = момент события; он сохраняется в плане как `PlanResult.not_before`, и `validate_plan` проверяет расписание по тому же правилу |
| вторая ступень работала только для аварий: заявку, выбитую из плана затянувшейся работой или выбывшим инженером, никто не пробовал разместить вытеснением | `_reclaim_displaced` — вытеснение для всех, кого событие оставило без исполнителя; заявки, неназначенные и до события, не трогаются |
| ключ `«IP-адрес 169...»` в справочнике был недостижим: у искомого значения точки срезались, у ключа — нет | ключи `work_types.json` нормализуются при загрузке так же, как значения выгрузки |

### Внешний аудит

Третий заход — прогон сторонним аудитором поверх зелёного сьюта, в несколько подходов.
Каждая находка проверена на живом коде и закрыта регрессионным тестом:

| находка | решение |
|---|---|
| авария под номером **уже назначенной** заявки раздваивала визит: `apply_event` подменял заявку, а прежний визит оставался в маршруте, и авария вставлялась рядом. `constraints_valid` при этом был `True` | переобъявленный незамороженный визит снимается при восстановлении плана (`drop_ids`), повторная вставка уже назначенной заявки отсекается на трёх уровнях (`insert_checked`, `place_single`, `place_with_ejection`); авария под номером **начатой** заявки отклоняется целиком — подменить объект нельзя, замороженный визит хранит пробег до прежнего адреса |
| отказ клиента посреди работы не обрезал расписание: замороженный визит держал плановое `service_end_at`, и освободившийся хвост дня не двигался | отказ по свершившемуся визиту порождает факт окончания, как `VISIT_COMPLETED`; отказ «в пути» заканчивает работу там же, где она по плану начиналась — поездка сохраняется, работа обнуляется |
| отказ клиента считал **стенные** часы: старт 12:00, обед 13–14, отказ в 14:00 давали норматив 120 минут вместо 60 рабочих | `_minutes_spent` удалён, отказ считается тем же `_minutes_worked`, что и завершение работ |
| `plan()` падал на грязном входе из глубины расчёта: `ZeroDivisionError` при нулевой скорости, `ValueError` из календаря при отрицательной длительности, `TypeError` при времени без зоны | время нормализуется в `__post_init__` четырёх моделей, числовая чушь отвергается на модели с указанием заявки или режима транспорта |
| ручной `reassign()` подписывал `diff` типом `urgent_request`: в журнале событий он выглядел как поступившая авария | отдельное значение `EventType.MANUAL_REASSIGN`; во вход `replan()` оно не допускается |
| `constraints_valid` оставался `True` на плане с дублем визита — флаг смотрел только на сходимость расписаний | к флагу добавлена уникальность назначений; в SPEC зафиксировано, что единственный полный оракул — `validate_plan` |
| факт вне графика (приезд в 19:00 при смене до 18:00) рисовал работу ночью молча | факт принимается как есть, но попадает в `warnings` отдельной строкой |
| проверка настроек закрыла только скорость: отрицательный `detour_factor` давал **отрицательный пробег** при пустом `validate_plan` (и `compare()` счёл бы это улучшением), `NaN` и бесконечность проходили любое сравнение с нулём, отрицательный `overhead_minutes` ронял расчёт из календаря | проверяются все три словаря по каждому режиму: ключ задан, значение конечно, `speed_kmh > 0`, `detour_factor > 0`, `overhead_minutes >= 0` |
| отказ клиента по несуществующему номеру молчал, хотя отмена такой же заявки предупреждала | оба события сообщают о неизвестной заявке одинаково |
| **верификатор противоречил планировщику**: пол `not_before` применялся только к началу маршрута, после начатого визита курсор вставал в его окончание и пол забывался. План, корректно поставивший работу на момент события, получал четыре расхождения подряд (выезд, прибытие, начало, конец). На авариях маскировалось: `received_at = event.at` сам прибивал старт к «сейчас» | пол применяется к каждой незамороженной работе — тем же правилом, что `RouteState.floor_m` |
| `NaN` и `inf` в длительности проходили проверку знака (`nan < 0` ложно) и падали из глубины: `int(timing.duration)` в объяснении отказа и `timedelta` | проверка на конечность идёт первой |
| выбытие инженера с неизвестным id молчало, хотя `diff.summary` рапортовал «Инженер стал недоступен» | предупреждение наравне с отменой и отказом |
| статус в обеденный перерыв описывался как выход за пределы смены | три случая различаются: до смены, после смены и перерыв — у последнего называется момент, с которого работа продолжится |
| отрицательный километр в матрице, подставленной снаружи, доходил до метрик молча: верификатор смотрит ту же матрицу и расхождения не видит | `MatrixTravelModel` проверяет оба словаря на конечность и неотрицательность |
| **отмена уже начатой работы телепортировала инженера в офис**: заявка исчезала из сценария целиком, а вместе с ней из маршрута — точка, в которой человек физически стоит. На стенде «инженер работает в 100 км от офиса» следующая заявка выезжала из офиса: 108 км и четыре часа вместо 1.7 км. `validate_plan` молчал — он считает по тому же усечённому сценарию. Отказ клиента в той же ситуации визит сохранял | отмена по свершившемуся визиту ведёт себя как отказ: визит остаётся в маршруте как состоявшийся, норматив урезается до отработанного, диспетчер получает предупреждение. Не начатая заявка по-прежнему снимается целиком |
| снятие работы событием, пришедшим **после** планового окончания, растягивало визит до момента события: час между окончанием работы и звонком диспетчера засчитывался как работа, и замороженный хвост дня уезжал вправо (дефект был и у отказа клиента) | общий `_removal_moment`: момент снятия обрезан границами самого визита — снизу началом работ, сверху плановым окончанием |
| `duration_minutes=True` проходило: `bool` — подкласс `int`, и заявка получала длительность в одну минуту. Из JSON это приходит буквально | `bool` отвергается по типу, до проверок на конечность и знак |
| неполная матрица перемещения: километры из словаря, минуты из `fallback` — «100 км за 13 минут» при пустом `validate_plan` | словари расстояний и минут обязаны знать одни и те же пары точек; `fallback` берётся только когда пара неизвестна обеим |

Три находки аудита разобраны и признаны не багами: ожидание у клиента во время перерыва
действительно не видно в занятости (следствие правила «в перерыв время не течёт», при этом
выезд даёт самый ранний возможный старт), а `feasible_count` совпадает с `assigned_count` по
построению. Оба упрощения переехали из докстрингов тестов в «Известные ограничения» README.

### Ранее открытые расхождения

Два места когда-то помечались `xfail(strict=True)`. Сейчас маркеров `xfail` в сьюте нет: тесты либо проходят, либо переписаны под актуальный контракт.

Отдельно проверяется **сам верификатор**: `test_invariants.py` портит заведомо корректный план
шестью способами (окно, пересечение работ, нумерация позиций, пропавший `Assignment`, чужой
инженер, подменённый пробег) и требует, чтобы `validate_plan()` это заметил. Без этого все
утверждения вида `validate_plan(...) == []` ничего не стоили бы.

## Принципы, которых придерживается сьют

* Один тест — одна мысль; имя вида `test_<что>_<ожидание>`; докстринг объясняет, **почему**
  это важно, а не что делает код.
* Там, где проверяется корректность плана, используется `validate_plan(result, scenario)`
  и требуется пустой список нарушений — независимая проверка вместо доверия внутренним
  структурам планировщика.
* Ни один тест не обращается к приватным атрибутам `planner`.
* Все случайные данные детерминированы фиксированным `seed`; `random` без seed не
  используется нигде.
* Волатильные поля (`computation_ms`, `plan_id`) исключаются из сравнения прогонов через
  `factories.normalized_dict()` — сам `to_dict()` при этом не подменяется.
