# Тесты планировщика `planner`

Сьют написан **строго по `solution/SPEC.md`**: имена классов, полей и функций берутся
оттуда буква в букву. Тесты не подстраиваются под реализацию — расхождение между SPEC и
кодом должно быть видно как красный тест, а не спрятано.

## Как запускать

Из корня репозитория (`E:\Programming\ЛЦТ 2026`):

```bash
python -m pytest solution/tests -q            # весь сьют
python -m pytest solution/tests -q -m "not slow"   # быстрый прогон (без нагрузочных)
python -m pytest solution/tests/test_replan.py -v  # один файл
python -m pytest solution/tests -q -m property     # только property-style прогоны
```

`conftest.py` сам добавляет `solution/` в `sys.path`, отдельной установки пакета не нужно.
Конфигурация лежит в `solution/tests/pytest.ini` — корень репозитория не затрагивается.

Маркеры: `slow` (дольше ~1 с), `property` (псевдослучайные сценарии), `realdata` (чтение CSV
из каталога `Обезличивание`). Внешних зависимостей, кроме `pytest`, нет.

## Инфраструктура

| файл | назначение |
|---|---|
| `conftest.py` | `sys.path`, общие фикстуры (каталоги, таймзона, дата сценария) |
| `factories.py` | билдеры `eng`/`req`/`sc`/`event`, независимые «оракулы» (гаверсинус, время в пути, рабочий календарь), генератор псевдослучайных сценариев, утилиты доступа к результату |
| `pytest.ini` | регистрация маркеров, `--strict-markers` |

`factories.py` терпимо резолвит публичные имена из `planner`, `planner.enums`, `planner.models`,
`planner.result`, `planner.calendar`, `planner.travel`, `planner.feasibility`, `planner.cost`.
Если пакет отсутствует или в нём нет нужного имени — тест-модуль **скипается** с внятной
причиной, а не разваливает коллекцию.

Оракулы в `factories.py` (`oracle_haversine_km`, `oracle_travel_minutes`, `OracleCalendar`)
реализованы независимо от `planner`, чтобы формулы SPEC проверялись, а не повторялись.

Дефолты билдеров: дата **2026-08-17**, пояс **UTC+3**, время задаётся строками `"HH:MM"`.
`sc()` по умолчанию перенумеровывает `input_order` по позиции в списке — именно от него
зависит baseline и все tie-break'и.

## Что сьют нашёл и что из этого вышло

Первый прогон дал 6 падений; все шесть оказались настоящими расхождениями SPEC ↔ реализация
и были исправлены в `planner`, а спорные места — зафиксированы в SPEC:

| находка | решение |
|---|---|
| `contains(13:00)=True`, но `first_moment_at_or_after(13:00)=14:00` | границы интервала включительны **везде**: `contains`, `first_moment_at_or_after`, `add(t,0)`, `sub(t,0)` |
| `sub(t, 0)` в начале интервала возвращал `None` | обратимость `add`/`sub` восстановлена |
| `no_engineers` при непустом списке инженеров (все `active=False`) | статические проверки идут по всем инженерам входа; теперь `no_work_time` |
| после `CLIENT_REFUSAL` план не проходил `validate_plan` | ремонт валидируется против сценария из `apply_event()`, а не против исходного |
| `PlanDiff` объявлял изменённый маршрут неизменным | подпись маршрута в diff учитывает `service_end_at` |

### Ревью кода и документации

Второй заход — сверка кода с базой знаний и с реальными выгрузками. Пять расхождений,
на каждое добавлен регрессионный тест:

| находка | решение |
|---|---|
| ожидание у клиента списывалось в занятость: маршрут из четырёх заявок показывал 97 % загрузки при реально свободном дне | выезд откладывается до начала работ, свободное время видно как `Visit.idle_before_minutes` |
| допуск календаря (1e-9 мин) был мельче разрешения `datetime`, и round-trip «минуты → datetime → минуты» перепрыгивал через обед: 13:00 превращалось в 14:00 | допуск поднят до 1e-6 минуты — крупнее микросекунды, но незаметен для расписания |
| расписание пересчитывалось от начала смены целиком, поэтому исчезновение раннего визита сдвигало **начатые работы** в прошлое | locked-префикс переносится из прошлого плана как факт (`RouteState.adopt`), верификатор такие визиты не пересчитывает |
| `apply_event` не двигал границу снимка, и после события заявка попадала в маршрут, но выпадала из назначений и метрик | `as_of = max(as_of, event.at)`; верификатор проверяет, что у каждого визита есть `Assignment` |
| норматив брался по HD раньше, чем по BK: 126 строк из 413 реальных выгрузок получали чужую длительность («Нет линка» — 80 мин вместо 30) | разбор «точная пара → BK → HD → default»; вид работ и норматив только по BK, HD уточняет снаряжение |
| `ejection_depth` вытеснял ровно одну заявку при любом значении | вытеснение идёт по нарастающей до заданной глубины; при 2 авария освобождает два слота подряд |
| ключ `«IP-адрес 169...»` в справочнике был недостижим: у искомого значения точки срезались, у ключа — нет | ключи `work_types.json` нормализуются при загрузке так же, как значения выгрузки |

### Ранее открытые расхождения

Два места когда-то помечались `xfail(strict=True)`. Сейчас маркеров `xfail` в сьюте нет: тесты либо проходят, либо переписаны под актуальный контракт.

Отдельно проверяется **сам верификатор**: `test_invariants.py` портит заведомо корректный план
шестью способами (окно, пересечение работ, нумерация позиций, пропавший `Assignment`, чужой
инженер, подменённый пробег) и требует, чтобы `validate_plan()` это заметил. Без этого все
утверждения вида `validate_plan(...) == []` ничего не стоили бы.

## Принципы, которых придерживается сьют

* Один тест — одна мысль; имя вида `test_<что>_<ожидание>`; докстринг объясняет, **почему**
  это важно, а не что делает код.
* Там, где проверяется корректность плана, используется `validate_plan(result, scenario)`
  и требуется пустой список нарушений — независимая проверка вместо доверия внутренним
  структурам планировщика.
* Ни один тест не обращается к приватным атрибутам `planner`.
* Все случайные данные детерминированы фиксированным `seed`; `random` без seed не
  используется нигде.
* Волатильные поля (`computation_ms`, `plan_id`) исключаются из сравнения прогонов через
  `factories.normalized_dict()` — сам `to_dict()` при этом не подменяется.
