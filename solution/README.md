# `planner` — алгоритм планирования рабочих маршрутов инженеров

Ядро решения кейса «Билайн Бизнес»: одна функция получает список заявок, список инженеров
и параметры дня, а возвращает всё, что нужно для маршрутов, расписаний, карты, метрик и
объяснений.

```python
from planner import plan, replan, compare, validate_plan, Algorithm

optimized = plan(scenario)                      # основной расчёт
baseline  = plan(scenario, Algorithm.BASELINE)  # базовый вариант из ТЗ, для сравнения
compare(baseline, optimized)                    # сравнение по обязательным метрикам
validate_plan(optimized, scenario)              # независимая проверка: [] = нарушений нет
replan(optimized, scenario, event)              # пересчёт после события дня
```

Ручная правка готового плана на Ганте — `planner.dispatch.Board`: маршруты
восстанавливаются из сохранённого расписания, `slots()` заранее отдаёт окна «когда можно
начать» по инженерам и позициям (интерфейс проверяет перетаскивание по ним без запросов),
`move()` делает ход — проверкой с превью или насовсем.

Зависимостей нет — только стандартная библиотека Python 3.10+. Ни сети, ни БД, ни ключей
API для запуска не требуется. Реальная маршрутизация по улицам подключается опционально
(свой openrouteservice, см. ниже) и тоже без внешних пакетов и ключей.

## Постановка

Задача — **TRSP** (Technician Routing and Scheduling Problem), то есть VRPTW плюс
требования к исполнителю. Отличия от хрестоматийного VRPTW, которые упрощают решение:

* маршруты **открытые** — возврат в офис не планируется (ТЗ п. 2.4);
* нет ограничения вместимости — вместо него жёсткая привязка исполнитель ↔ навык ↔ транспорт;
* число «машин» фиксировано и равно числу инженеров, у каждого свой старт и своя смена;
* допускается **отказ от части заявок** — но с обязательным объяснением причины.

Из этого следует, что промышленный MIP-солвер не нужен: задача хорошо решается
конструктивной эвристикой с последующим локальным поиском.

### Жёсткие ограничения

Проверяются все четыре группы, каждая — в одной-единственной функции `check_static`,
которую используют и базовый алгоритм, и конструктивная фаза, и локальный поиск, и
перепланирование. Дублировать проверки нельзя: расхождение между ними — самый дорогой
класс ошибок, потому что план внешне выглядит корректным.

| Группа | Правило | Код причины |
|---|---|---|
| Территория | регион инженера = регион заявки (межрегиональные назначения запрещены) | `no_region` |
| Квалификация | требуемый навык входит в навыки инженера | `no_skill` |
| Ресурс | если в заявке задан транспорт — он совпадает с транспортом инженера | `no_transport` |
| Ресурс | требуемое снаряжение выдано инженеру на день (опционально) | `no_equipment` |
| Время | прибытие ≤ конца окна; работа целиком в рабочем времени смены | `time_conflict` |

Территория — не «лишнее» ограничение: база знаний прямо запрещает межрегиональные
назначения, а ТЗ ограничивается тремя группами. Проверка включается флагом `check_region`.

### Модель времени

Окно `Начало`–`Окончание` — это окно **прибытия**, а не длительность работы.

* **выезд откладывается**: инженер выезжает так, чтобы приехать к началу работ, а не
  освободился — поехал. Иначе он стоит у подъезда два часа, это ожидание попадает в
  занятость, и маршрут из четырёх заявок показывает 97 % загрузки при реально свободном дне.
  Свободное время остаётся простоем **до** выезда (`Visit.idle_before_minutes`);
* приехал позже `window_end` → в окно не попал, вариант отвергается;
* алгоритм окна сам не сдвигает: расчёт берёт актуальное окно из сценария, старый план сохраняет своё; заявки автоматически не отменяются;
* закрытые (выполненные и отменённые) в новый план не входят;
* если окно плюс норматив не влезают в смену ни одному инженеру, заявку не выполнить
  ни при каком распределении — план говорит это отдельным предупреждением, а объяснение
  отказа не сваливает причину на загрузку. В предоставленных выгрузках есть окна прибытия
  до 22:00, поэтому смена по умолчанию в `demo.py` — 09:00–22:00: при 09:00–21:00 пять
  заявок «Востока», включая две аварии, отбрасываются арифметикой, а не алгоритмом;
* длительность обслуживания — технические работы и документы **без** дорожных 20 минут
  из Excel: подключение 70, авария 80, дозаказ 20, локальная 30; дорога считается отдельно;
* работа не начинается раньше окна прибытия **и** момента поступления (`received_at`);
  авария, поступившая в 13:00, не выполняется до поступления и не входит в снимок плана на 09:00;
* и работа, и перемещение расходуют только рабочее время: перерыв в середине дня не «съедает»
  дорогу, время в нём не течёт.

Откат выезда ограничен с двух сторон: раньше, чем инженер освободился, выехать нельзя,
и позже `window_end` прибыть нельзя. Поэтому он не меняет ни допустимость визита, ни время
начала работ — только убирает бессмысленное стояние у клиента и делает `free_minutes`
и `utilization` честными.

Последнее реализовано классом `WorkCalendar`, который умеет складывать и вычитать
**рабочие** минуты. Благодаря этому перерывы и рваные графики поддерживаются без единого
особого случая в самом алгоритме.

## Алгоритм

### Базовый вариант (обязателен по ТЗ п. 2.3)

Заявки в порядке поступления → первому подходящему инженеру по порядку входа, всегда в конец
маршрута. Порядок посещения = порядок назначения. Никакой оптимизации. Нужен не как запасной
вариант, а как честная точка отсчёта: без него нельзя показать, что оптимизация что-то дала.

### Оптимизированный вариант

```
1. regret-вставка            строит допустимое решение, стараясь не терять заявки
2. локальный поиск           сокращает время в пути и пробег
3. минимизация парка         освобождает инженеров, не теряя ни одной заявки
4. локальный поиск повторно  прибирает маршруты после переносов
```

**1. Конструктивная фаза — regret-k insertion.** На каждом шаге размещается не первая
попавшаяся заявка, а та, которую **опаснее всего откладывать**: у которой разрыв между
лучшим и k-м по качеству вариантом наибольший. Заявка с единственным возможным исполнителем
получает бесконечное «сожаление» и ставится первой. Это ровно то место, где жадный алгоритм
теряет заявки — он занимает единственного подходящего инженера чем-то другим. Аварии
рассматриваются раньше подключений, подключения — раньше ремонта и дозаказа.
Если авария всё равно не влезает, она **сдвигает** хвост маршрута; когда окна остальных
не держат сдвиг — вытесняет менее приоритетные работы, до `ejection_depth` подряд. Тот же
механизм (`place_with_ejection`) — вторая из трёх ступеней ремонта при событии «Аварийная
заявка» в разделе «Перепланирование» ниже.

Объяснение диспетчеру звучит так же коротко: *«эту заявку поставили раньше остальных, потому
что запасных вариантов у неё почти не было»*.

**2. Локальный поиск.** Четыре классических оператора VRPTW: `or-opt` (перенос 1–3 подряд
идущих заявок внутри маршрута), `2-opt` (разворот участка), `relocate` (перенос между
маршрутами), `exchange` (обмен заявками). После каждого раунда — повторная попытка пристроить
неназначенные заявки: перестановки освобождают время, и заявка, не влезавшая после
конструктивной фазы, часто помещается.

**3. Минимизация числа исполнителей** — то, чего regret-вставка сама не обеспечивает: она
оптимизирует стоимость каждой вставки по отдельности и легко «размазывает» день по всем
инженерам. Приём стандартный для задач минимизации парка — *route elimination*: берём самый
лёгкий маршрут, распускаем его и пробуем разложить заявки по остальным, **не открывая никого
нового**. Разошлись все — инженер свободен на весь день, повторяем. Нет — откатываемся
целиком. Число назначенных заявок при этом не имеет права уменьшиться.

Именно эта фаза даёт в таблице выше 12 → 11 и 11 → 9 инженеров.

### Порядок критериев — структурой, а не весами

Стоимость вставки — не взвешенная сумма, а **лексикографический вектор**:

```
(открывается ли новый инженер, Δ время в пути, Δ пробег, Δ ожидание)
```

Типовой приём «штраф за нового инженера = 100000» работает, но держится на подобранной
константе: стоит пробегу вырасти на порядок — и приоритеты молча меняются местами. Здесь
порядок выражен структурой данных, поэтому его нельзя нарушить случайно, и он прямо
проговаривается диспетчеру: *сначала не открываем нового человека, потом экономим время,
потом километры*.

Тот же принцип на уровне плана целиком (`PlanMetrics.quality_key`, меньше — лучше):

```
(аварий без исполнителя, подключений без исполнителя, всего без исполнителя,
 задействовано инженеров, время в пути, пробег)
```

Порядок соответствует базе знаний: авария → подключение → ремонт / дозаказ, затем
сокращение числа исполнителей, время перемещения важнее пробега.

У этого порядка есть осознанное следствие: **освобождение инженера ценится дороже любой
экономии километров**. Если два инженера стартуют из офисов в 60 км друг от друга, алгоритм
предпочтёт отправить одного объехать оба участка, лишь бы не занимать второго. Это ровно то,
что просит ТЗ («выполнение всех заявок наименьшим количеством персонала»), но на карте такой
маршрут выглядит непривычно. Если бизнес-приоритеты другие — порядок меняется в одном месте,
`Solution.quality_key()` и `InsertionCost`, без правок в самих алгоритмах.

### Бюджет времени

Общий лимит (`time_limit_seconds`, по умолчанию 5 с) делится между фазами заранее: 35 %
первому локальному поиску, 40 % минимизации парка, остаток — финальной доводке.
Без такого деления локальный поиск на трудном наборе съедает всё время, и минимизация числа
исполнителей — первая обязательная метрика ТЗ — просто не успевает запуститься.

В перепланировании лимит делится по той же причине: `global_replan_time_share` (по умолчанию
40 %) резервируется под третью ступень — пересчёт остатка дня, дешёвые ступени укладываются
в остаток. Если пересчёт не успел, правило приёмки просто оставит лучший из двух готовых
вариантов: отказа из-за лимита не бывает. Резерв тратится только тогда, когда третья
ступень вообще разрешена: `Settings.replan_scope` (`low` / `medium` / `high`, по умолчанию
`high`) — потолок лестницы ремонта, см. раздел «Перепланирование».

Алгоритм **anytime**: любая фаза может завершиться досрочно, решение останется допустимым —
каждая фаза поддерживает допустимость как инвариант, а не проверяет её в конце.

## Перепланирование

Требование ТЗ — новый план за минуты и наглядный показ того, **что именно** изменилось.
Пересчёт «с чистого листа» формально удовлетворяет первому и полностью проваливает второе:
диспетчер видит, что перетасовался весь день, и не может понять, это следствие события или
случайность эвристики. Поэтому — инкрементальный ремонт по общему каркасу:

```
заморозить прошлое → применить событие → починить только затронутое → показать разницу
```

**Заморозка** — ключевой инвариант: назначение, работа по которому началась до момента
события, не меняется ни по исполнителю, ни по времени. Такие визиты остаются в начале
маршрута как `locked` с их фактическим расписанием из прошлого плана: ни один оператор
поиска не имеет права их тронуть, и пересчёт не двигает их во времени. Замораживается и
визит, к которому инженер уже **выехал** (`departure_at < event.at`) — развернуть человека
на середине дороги можно только на бумаге. Исключение — инженер, выбывший по событию
«Инженер недоступен»: его поездка прервана вместе со сменой, поэтому недоеханный визит
освобождается и уходит в пул на переразмещение.

**Факт сильнее допущения.** Статусы исполнения («инженер на месте», «работы завершены»)
замораживают визит, к которому относятся, вместе со всем, что стоит в маршруте до него: раз
инженер доложил о третьей заявке, значит первые две он уже сделал. Возможен и обратный
случай — факт опровергает то, что план считал сделанным: работа затянулась до 12:00, а
следующий визит «по плану» должен был начаться в 11:00. Такой визит перестаёт считаться
начатым, возвращается в расчёт и планируется заново от фактического времени; иначе в
маршруте оказались бы две накладывающиеся друг на друга работы.

Ремонт идёт по той же лестнице, что и в основном расчёте, — точечная вставка, локальное
вытеснение, пересчёт остатка дня, — но при событии у неё появляется **потолок**:
`Settings.replan_scope` (`low` / `medium` / `high`, по умолчанию `high`) задаёт, до какой
ступени разрешено дойти, если дешёвые не справились. Лестница всегда начинается с самой
дешёвой ступени независимо от степени. При `low` вытеснение и стабилизирующий локальный
поиск не запускаются вовсе — план либо принимает заявку в свободное окно, либо честно
отказывает; при `medium` включается вытеснение и перестановки внутри затронутых маршрутов;
`high` добавляет пересчёт остатка дня по всем инженерам. Степень можно переопределить на
один вызов — `replan(..., scope="low")` перекрывает настройку сценария; диспетчеру это
кнопка «перестроить сильнее»: сначала низкая степень, и если заявку не удалось сохранить —
повторный вызов с высокой, уже осознанно соглашаясь на переставленный день.

| Событие | Что делает алгоритм |
|---|---|
| Аварийная заявка | ремонт по лестнице до потолка `replan_scope`: (1) точечная вставка в лучшую допустимую позицию; (2) при `medium`/`high` — локальное вытеснение до `ejection_depth` заявок меньшего приоритета подряд в одном маршруте; (3) при `high`, если авария всё равно без исполнителя — пересчёт остатка дня: у всех инженеров снимается неначатое, пул (снятые хвосты + ранее неназначенные + авария) раскладывается заново поверх замороженных префиксов. Третья ступень применяется только если она строго лучше по `quality_key()`, а при равном качестве — только если меняет меньше маршрутов, чем ремонт на ступенях 1–2; иначе остаётся дешёвый результат (авария важнее подключения, подключение — ремонта/дозаказа) |
| Отмена заявки | убирает визит, пересчитывает **только этот** маршрут — хвост сдвигается раньше |
| Инженер недоступен | смена обрезается моментом события (но не раньше конца начатых работ), осиротевшие заявки проходят regret-вставку **только по оставшимся** инженерам; если после этого что-то из ранее назначенного осталось без исполнителя — та же ступень 3, что и для аварии, с тем же правилом приёмки |
| Отказ клиента на адресе | поездка сохраняется, работа не засчитывается, освободившееся время отдаётся остатку маршрута |
| Инженер на месте (`VISIT_ARRIVED`) | состав заявок не меняется — визит остаётся в плане. Прибытие подставляется из `event.at`, начало работ достраивается от него по обычным правилам (не раньше открытия окна, не в перерыв), визит и всё, что стоит перед ним в маршруте, замораживается; молчание диспетчера значит «идёт по плану», и ничего не двигается |
| Работы завершены (`VISIT_COMPLETED`) | окончание визита = `event.at`; фактическая длительность считается по рабочим минутам между началом работ и моментом события (обед посреди работы не засчитывается) и записывается в `duration_minutes` заявки, как и при отказе клиента. Расхождение с нормативом попадает в `warnings`. Хвост маршрута пересчитывается от факта: если работа затянулась, следующие визиты сдвигаются, а те, что перестали помещаться в окно или смену, идут по той же лестнице ремонта, что и авария — свободное окно, вытеснение, пересчёт остатка дня |

Вторая ступень (локальное вытеснение) работает не только для аварий: любая заявка, которую
событие выбило из плана — была назначена в прошлом плане, а теперь без исполнителя, —
пробует вытеснить менее приоритетную работу. Заявки, которые были без исполнителя ещё до
события, этой ступенью не трогаются: событие их положение не ухудшило.

Результат — `PlanDiff`: какие назначения, маршруты и времена изменились, что удалено, что
осталось **без изменений**. На реальных наборах аварийная заявка затрагивает 1 маршрут из 11.

Ремонт по событию не может назначить работу раньше момента события: у каждого маршрута
есть «пол» (`RouteState.floor_m`), и то, что ещё не началось, не может встать раньше него.
Момент сохраняется в результате как `PlanResult.not_before` (у расчёта с нуля — `None`,
там ограничения нет) и попадает в JSON плана; верификатор `validate_plan` проверяет
расписание по тому же правилу, что и планировщик.

Событие меняет и сами входные данные: аварийная заявка добавляется с `received_at` события,
отменённая исчезает, у заявки с отказом клиента обнуляется работа. Действующий после события
сценарий отдаёт публичная `apply_event(scenario, previous, event)` — та же функция, что применяет `replan`
внутри. Проверять результат ремонта нужно против него:

```python
after = replan(before, scenario, event)
effective, notes = apply_event(scenario, before, event)
validate_plan(after, effective)      # [] — нарушений нет
```

## Объяснения

Собираются **из тех же данных, что использовал алгоритм**: причина отказа — это код, который
вернула единая функция проверки, а не отдельно сочинённый текст. Объяснение невозможно
рассинхронизировать с решением, и на защите его можно показать «по коду».

> Заявка 86160 назначена инженеру Бригада Комарь: у него есть навык «Работы на подключение и
> дозаказы». Приезжает в 19:35 (окно 18:00–20:00), работает с 19:35 до 20:45 и укладывается
> в смену до 21:00. Маршрут удлиняется на 1.8 км — это минимум среди 8 подходящих исполнителей.

> Заявка 74198 не назначена: ни один инженер с навыком «Работы на подключение и дозаказы»
> не успевает в окно 20:00–22:00 с учётом уже запланированных работ и времени в пути.
> Проверено: Бригада Арташкин освобождается в 20:47, и смена заканчивается раньше, чем он
> успеет доехать; у Бригада Гусаковский (2 заявки, освобождается в 14:50) не остаётся 70 мин
> в смене; …

Две детали, которые обычно упускают:

* **Причина — самая содержательная, а не первая сработавшая.** Если хоть один инженер дошёл
  до проверки времени, значит навык и транспорт в организации есть, и честный ответ —
  «не помещается по времени», а не «нет навыка». Коды причин упорядочены по глубине
  пройденной проверки, побеждает максимальный ранг.
* **Причина пересчитывается по итоговому плану, а не по моменту неудачи.** Запись «не влезло»
  сделанная в начале расчёта, к концу устаревает: тогда маршруты были пустыми. Объяснение
  описывает тот план, который человек видит на экране.

Генерация текста языковой моделью здесь была бы хуже по трём причинам: недетерминирована,
непроверяема и способна уверенно описать ограничение, которого алгоритм не проверял.

## Маршрутизация по улицам (openrouteservice)

По умолчанию расстояния считаются по координатам. Это разрешено ТЗ (п. 2.4, п. 3.2) и даёт
запуск без сети, но у допущения есть цена: один коэффициент извилистости на весь регион не
знает ни про реку, ни про железную дорогу, ни про односторонние улицы — и по прямой нельзя
нарисовать маршрут на карте.

[openrouteservice](https://github.com/GIScience/openrouteservice) (GPL-3.0/LGPL-3.0,
данные OpenStreetMap, разворачивается своим `docker compose`) закрывает обе задачи:

| Что нужно | Эндпойнт ORS | Куда попадает |
|---|---|---|
| расстояния и времена по улицам | `POST /v2/matrix/{profile}` | `OrsTravelModel` → `plan(scenario, travel=...)` |
| линия маршрута для карты | `POST /v2/directions/{profile}/geojson` | `RouteResult.geometry`, `Visit.geometry_range` |
| поездка на транспорте по расписанию | `POST /v2/directions/public-transport/geojson` + `departure` | `OrsTravelModel`, `Visit.transit` |

Способы передвижения из справочника ТЗ п. 2.4.1 отображаются на профили ORS один к одному
(`planner/ors.py: DEFAULT_PROFILES`): автомобиль → `driving-car`, пешком → `foot-walking`,
велосипед → `cycling-regular`, общественный транспорт → `public-transport`.

### Общественный транспорт считается по расписанию

Матрицу для него брать нельзя: в `/v2/matrix` нет параметра времени отправления, поэтому
расписания в неё не попадают и ORS отдаёт по ней пешее время — внешне неотличимо от
рабочего ответа, числа приходят правдоподобные, просто не те (Медведково — Ясенево:
матрица 428 минут, пешком 427, по расписанию 63). Такие профили перечислены в
`planner/ors.py: NO_MATRIX_PROFILES`, и матрица по ним не запрашивается.

Ограничение относится к матрице, а не к профилю: `/v2/directions` время отправления
принимает. Поэтому у общественного транспорта источник чисел другой — тот же `directions`,
но по одной паре точек за запрос (`fetch_transit_legs`). Дороже: ~4 000 запросов на набор
вместо одного; на всех трёх наборах это около получаса в восемь потоков. Платится один
раз — дальше всё лежит в `data/routing_cache.json`, и расчёт идёт офлайн:

```bash
python tools/ors_prefetch.py --transit     # разовый прогрев, потом кэш
python demo.py                             # расписания уже используются, без флагов
```

Тем же ответом приходит **состав поездки**, и он доезжает до плана — `Visit.transit`.
Та же пара Медведково — Ясенево:

```
пешком 4 мин
автобус 601 от «МФЦ Северное Медведково», 3 ост., 5 мин   10:05→10:10
пешком 1 мин
метро Калужско-Рижская линия от «Медведково», 22 ост., 50 мин   10:12→11:02
пешком 0 мин
```

Диспетчер видит не только «в пути 63 минуты», но и на чём ехать и где садиться.
`demo.py` печатает это под каждым визитом, карта — в карточке визита.

### Что это изменило в планах

Одни и те же сценарии, отличается только источник чисел для общественного транспорта
(смена 09:00–22:00, лимит поиска 5 с):

| Набор | Общественный транспорт | Назначено | Заявок у ОТ | В пути у ОТ, мин | Покрытие реальными данными |
|---|---|---|---|---|---|
| Восток | по прямой | 60 | 19 | 456 | 63 % |
| Восток | **по расписанию** | 61 | **14** | 511 | **100 %** |
| Юго-восток | по прямой | 45 | 9 | 1389 | 81 % |
| Юго-восток | **по расписанию** | 45 | 9 | 1391 | 83 % |
| Югоцентр | по прямой | 55 | 18 | 398 | 64 % |
| Югоцентр | **по расписанию** | 54 | **15** | 459 | **100 %** |

Читать это надо так: **расчёт по прямой был оптимистичен**. 18 км/ч плюс 10 минут
накладных — это скорость, с которой по городу не ездят: она не знает ни ожидания рейса,
ни пересадки, ни подхода к остановке. Инженеру на общественном транспорте план ставил
19 заявок там, где он успевает 14, и на «Югоцентре» одна заявка из-за этого ушла в отказ.
Заявок в плане не прибавилось — прибавилось выполнимости: то, что раньше держалось на
заниженном времени в пути, теперь держится на расписании.

«Юго-восток» почти не изменился, и это тоже правильный ответ: его адреса в Кашире и
Ступине вне зоны действия фида, связать их расписанием нечем, и они остаются на расчёте
по координатам — с пометкой в `warnings`, а не молча.

Один важный нюанс, который легко пропустить: **ORS читает `departure` без зоны как UTC**,
а план живёт в московском времени. Без перевода запрос уезжал бы на три часа вперёд —
выезд в 09:00 считался бы по расписанию полудня. Перевод делает `transit_moment`.

Матрица считается на один опорный час (`PT_DEPARTURE_HOUR`, 10 утра), а конкретный
маршрут диспетчеру показывается на фактическое время выезда из расписания плана —
поэтому и раздел кэша у поездки свой, со временем в ключе.

### Расписание привязано к дате плана

Раздел кэша расписаний называется `public-transport@2026-08-17T07:00:00` — профиль плюс
момент отправления в UTC. Дата в ключе обязательна: одна и та же пара точек в будний день
и в воскресенье — разные интервалы движения, и складывать их в одну таблицу нельзя.

У этого есть обратная сторона, и она опаснее. План на **другой день** не находит в таком
кэше ничего — даже когда кэш полон на соседнюю неделю. Внешне такой план не отличается
ничем: те же маршруты, те же визиты; меняются только числа, потому что поездка на метро
тихо превращается в расчёт по прямой. Поэтому тихого исхода здесь нет ни одного:

| Что в кэше | Что делает расчёт | Что пишется в `warnings` |
|---|---|---|
| нужный момент | берёт его | момент, на который посчитано, и сколько пар закрыто |
| тот же день недели и час, другая дата | берёт как **приближение** | обе даты, слово «приближение» и чего оно не учитывает |
| другой день недели или час | считает по координатам | что именно лежит в кэше и команда прогрева с датой |
| ничего | считает по координатам | команда прогрева |

Приближение по дню недели — сознательный выбор, а не лазейка. Разница между двумя
понедельниками в августе и сентябре (праздники, ремонты, новые маршруты) несравнимо
меньше, чем разница между поездкой по расписанию и расчётом по прямой, ради которой
пришлось бы выбросить весь прогретый кэш. Но названа она всегда — подмена, о которой
не сказали, это не приближение, а ошибка.

Прогреть кэш на нужный день:

```bash
python tools/ors_prefetch.py --transit --date 2026-09-21   # можно повторять --date
```

Проверяется это `tests/test_ors.py`: «тот же понедельник» переиспользуется и называет обе
даты, вторник вместо понедельника не переиспользуется вовсе, а офлайновый расчёт
(`setup_routing` без адреса сервиса) на чужую дату не молчит.

### Что пишется в отчёт, когда числа не настоящие

Откат на расчёт по координатам сам по себе ничего не говорит: у него три разные причины,
и действия у диспетчера по ним разные. Поэтому они считаются врозь и врозь попадают в
`PlanResult.warnings` (`planner/ors.py: TransitFailures`):

| Причина | Как выглядит в отчёте | Что с этим делать |
|---|---|---|
| вердикт сервиса о паре точек | «адрес вне зоны действия фида» | ничего: Кашира с московским фидом не свяжется никогда |
| сервис не ответил (сеть, таймаут, 5xx без кода ORS) | «из-за отказа сервиса (текст ошибки)» | поднять контейнер и пересчитать |
| вердикт не про адреса, а про запрос или профиль (`REQUEST_LEVEL_CODES`, например 2003 «нет такого профиля») | «запросов расписания сервис отклонил» | смотреть `ors-config.yml`; пересчёт плана не поможет |
| ответ 200 без расстояния или времени | «без расстояния или времени в пути» | смотреть инстанс: профиль отвечает, но не измеряет |

Раньше все четыре писались одной строкой «не связал по расписанию (адрес вне зоны
действия фида)», и таймаут выглядел для диспетчера ровно как Кашира.

Различает их код ошибки ORS, и перечисляется в коде намеренно то, что относится к
**запросу**, а не то, что относится к точкам (`planner/ors.py: REQUEST_LEVEL_CODES`,
`is_point_verdict`). Это второй заход, и первый стоил дорого. Сначала перечислялись
«коды про пару точек», и каждый неучтённый код молча превращался в поломку профиля.
Так вскрылись 2014 («PT exit point cannot be reached» — вне фида адрес прибытия) и
2013 («PT entry point…» — вне фида адрес отправления): 2538 пар «Юго-востока» уехали в
отчёт как отказ сервиса с советом пересчитать план, когда сервис поднимут, — а он и не
падал. Хуже того, `PROFILE_STRIKES` считал такой ответ поломкой профиля, и трёх
адресов вне фида подряд хватало, чтобы у всего набора перестала строиться линия
общественного транспорта: строилось 2 участка вместо сотни.

Перечень «про запрос» конечен и от данных не зависит; перечень «про точки» растёт с
каждым новым типом местности, и угадать его заранее нельзя. Поэтому умолчание для
незнакомого кода теперь безопасное — «вердикт о паре точек», то есть продолжаем
работать. Цена ошибки в эту сторону — несколько лишних запросов на прогреве; в
обратную — потерянная геометрия целого набора.

Итог по покрытию тоже разбит по способам передвижения, и у расписаний назван момент:

```
ORS: 16 из 5627 обращений к расстояниям посчитаны по координатам (покрытие матрицей 99.7%)
ORS: «общественный транспорт»: по расписанию на 17.08.2026 10:00 (понедельник)
     посчитано 1710 пар из 1726, остальные 16 — по координатам
```

`tools/ors_check.py` показывает обе колонки сразу: матрица помечается словом «пешком!»
(это норма), а колонка «маршрут» печатает время по расписанию и номера маршрутов. Если
«пешком!» появилось и там — расписания в граф не попали, и это уже поломка.

И матрица, и геометрия кэшируются по УЧАСТКАМ — парой «откуда→куда». Для линии маршрута
это один запрос `directions` на участок вместо одного на весь маршрут: запросов в
несколько раз больше (холодный прогрев трёх регионов по двум планам — 245 против 55),
и это сознательный размен на две вещи.

Во-первых, непостроенный участок стоит участка, а не всей линии: он заменяется прямой,
маршрут помечается `geometry_source: "mixed"`. Раньше `directions` получал все точки
разом и отказывал целиком, если хоть одна пара не связывалась, — из-за адресов в Кашире
и Домодедово линию теряли 4 маршрута из 55, стало 2. Во-вторых, кэш не обнуляется от
перестановки визитов: после снятия одной заявки и перепланирования ключ по маршруту
переиспользовал 9 линий из 27, ключ по участкам — 84 участка из 159.

На чём выигрыша нет: базовый и оптимизированный планы делят между собой лишь 2%
участков — они развозят разные заявки разными инженерами.

### Подключение

```bash
cd deploy/ors && ./download-osm.sh && docker compose up -d   # инструкция: deploy/ors/README.md
python tools/ors_check.py                                   # что умеет инстанс
python demo.py --ors                                        # расчёт по улицам
python viz/export.py --ors                                  # выгрузка для карты с линиями
python tools/ors_prefetch.py --with-geometry                # прогреть кэш и работать офлайн
```

В коде это три строки, и ни одна из них не в алгоритме:

```python
routing = setup_routing(scenario, url="http://localhost:8081/ors")
result = routing.attach(plan(scenario, travel=routing.travel))   # расчёт + геометрия
routing.save()                                                   # ответы сервиса — в кэш
```

### Что гарантируется

* **Алгоритм не меняется.** ORS подставляется через тот же протокол `TravelModel`, что и
  расчёт по координатам. Конструктивная фаза, локальный поиск, перепланирование и проверки
  работают с ним, не зная о его существовании.
* **Расчёт не падает из-за сервиса.** Контейнер выключен, профиль не собран, точка не легла
  на граф — соответствующее перемещение считается по координатам, а факт отката попадает в
  `PlanResult.warnings` с указанием доли таких обращений. План строится всегда.
* **Ответ 200 неожиданной формы — тоже отказ, а не исключение.** `"distance": "нет"`,
  пустой `summary`, ряд матрицы короче самой матрицы — всё это разбирается как «сервис
  не сказал» и кончается расчётом по координатам (для линии — прямой) и строкой в
  `warnings`. В частности, пустой `summary` НЕ сохраняется как поездка в 0 км и 0 минут:
  такая пара попала бы в кэш, то есть навсегда, и стала бы бесплатным переездом через
  весь город — причём в плане это выглядело бы как удача.
* **Причина отката называется.** Граница фида, отказ сервиса и неразбираемый ответ — три
  разные строки в `warnings`, а не одна (см. «Что пишется в отчёт, когда числа не
  настоящие»).
* **Направление сохраняется.** Матрица ORS не симметрична (односторонние улицы), и модель
  её не «выпрямляет»: A→B и B→A остаются разными числами.
* **Сопутствующие затраты остаются нашими.** Парковка, подход и подъём в квартиру —
  требование базы знаний, а не часть дорожного графа; `overhead_minutes` прибавляется к
  времени сервиса и настраивается отдельно.
* **Воспроизводимость сохраняется.** `tools/ors_prefetch.py` складывает ответы в
  `data/routing_cache.json` — так же, как `tools/geocode.py` складывает координаты. После
  прогрева расчёт идёт офлайн и детерминированно, контейнер для показа не нужен.

### Ключевые приёмы

**Проверка вставки за O(1).** Для каждого маршрута считается не только фактическое расписание
(прямой проход), но и «самый поздний допустимый старт» каждого визита (обратный проход).
Проверка «а не сломает ли вставка более поздние заявки» становится одним сравнением вместо
отдельного цикла протяжки времени, который легко забыть обновить при правке кода.

**Кэш вставок с точечной инвалидацией.** После вставки меняется ровно один маршрут, поэтому
пересчитывается только его столбец, а не вся матрица «заявка × инженер».

**Быстрая оценка — фильтр, прямой проход — истина.** Оценка вставки оптимистична на границах
перерывов, поэтому каждая фактическая вставка подтверждается полным пересчётом и
откатывается, если он не сошёлся. Ошибка в фильтре не может испортить план.

**Проверки встроены в мутацию, а не рядом с ней.** `RouteState` не даст положить в маршрут
заявку, которую инженер не имеет права выполнять, на **любом** пути изменения состава. Без
этого оператор переноса между маршрутами тихо отдаёт заявку инженеру без нужного навыка:
план остаётся корректным по времени и неисполнимым по сути.

## Проверка результата

`validate_plan(result, scenario)` — независимый верификатор. Он **не** использует внутренние
структуры планировщика: заново считает расписание каждого маршрута по определению из
спецификации и сверяет с тем, что план заявляет. Смысл — чтобы ошибка в оптимизаторе не могла
подтвердить сама себя. Пустой список = план корректен.

Проверяются все инварианты из `SPEC.md` § 9: покрытие всех заявок ровно одним результатом,
отсутствие двойных назначений, попадание в окна, границы смены, непересечение работ,
непрерывность нумерации визитов, сходимость заявленных времён и расстояний с пересчитанными,
наличие причины и объяснения у каждой неназначенной заявки.

| число задействованных инженеров | ✅ | `used_engineer_count` |
| сравнение базового и рассчитанного | ✅ | `compare()` |
| время перемещения и пробег | ✅ | суммарно и по каждому инженеру |
| **(Should)** сравнение нескольких вариантов | ⚠️ | `compare()` сравнивает два плана; сопоставление N вариантов не реализовано |

### Перераспределение

| Требование | Статус | Где |
|---|---|---|
| **(Must)** перестроение при аварийной заявке | ✅ | с вытеснением менее приоритетных при необходимости |
| **(Must)** учитывать приоритет при пересчёте | ✅ | авария → подключение → ремонт / дозаказ |
| **(Should)** ручное переназначение | ✅ | `reassign()` — с проверкой ограничений и отказом вместо тихого нарушения |
| **(Should)** перестроение после отказа клиента | ✅ | `CLIENT_REFUSAL` |
| **(Should)** перестроение при недоступности инженера | ✅ | `ENGINEER_UNAVAILABLE` |
| **(Could)** влияние новой заявки на план | ✅ | `PlanDiff` + `incremental_distance_km` |
| обновление плана по статусам исполнения | ✅ | `VISIT_ARRIVED` / `VISIT_COMPLETED`: время берётся из момента события, остаток маршрута и дня пересчитывается от факта; отсутствие статуса — «идёт по плану» |

### Как обойдены открытые вопросы базы знаний

| Вопрос | Решение в прототипе |
|---|---|
| смысл допустимого overbooking | не моделируется: план не допускает пересечения работ одного инженера. «Разрешение нарушать окна» из открытого вопроса не следует |
| шкала квалификации и её влияние | уровень хранится и показывается, на отбор не влияет; генерируется синтетически (`junior`/`middle`/`senior`) |
| порядок конфликтующих критериев | зафиксирован лексикографически: авария → подключение → объём → число людей → время → пробег. Меняется в одном месте |
| ограничивает ли конец окна начало обслуживания | флаг `service_must_start_within_window`, по умолчанию включён (строгая трактовка) |
| количество и расход оборудования | учитывается только факт наличия вида на день; расход не моделируется |
| источник фактических статусов | подключён как события перепланирования: «инженер на месте» (`VISIT_ARRIVED`) и «работы завершены» (`VISIT_COMPLETED`) подмешивают факт в план, время берётся из момента события, а не из отдельного поля факта. Отсутствие статуса по договорённости с диспетчером значит «идёт по плану» — молчание ничего не двигает |
| что фиксировать при пересчёте | замораживаются визиты, работа по которым началась до момента события |

## Известные ограничения и куда развивать

* **Глобальный оптимум не гарантируется** и не требуется по ТЗ. Качество можно поднять до
  уровня ALNS, добавив операторы разрушения/восстановления поверх той же `is_feasible`.
* **Расстояния по прямой** — это режим по умолчанию, а не потолок: `--ors` переключает
  расчёт на реальную сеть улиц (см. раздел «Маршрутизация по улицам»). По умолчанию режим
  остаётся прежним, потому что запуск без сети и без контейнера — требование к решению.
* **Время в пути не зависит от времени выезда** (нет пробочного профиля). Модель к этому
  готова: `TravelModel` можно расширить параметром времени отправления.
* **Квалификация по навыку** (уровень, а не факт наличия) в модели есть, но на выбор
  исполнителя не влияет — шкала и правило влияния в базе знаний пока не определены.
* **Overbooking** не моделируется: его точный смысл остаётся открытым вопросом, а
  «разрешение нарушать окна» из него не следует.
* **Снаряжение** учитывается как факт наличия вида на день; количество и расход по ходу дня
  требуют уточнения и не моделируются.
* **Простой между заявками не переиспользуется**: выезд откладывается, но вставить в
  освободившееся окно работу из другого конца города алгоритм не пытается — порядок визитов
  задаёт маршрут. Это следующий шаг: учитывать `idle_before_minutes` как ресурс при вставке.
* **`received_at` в выгрузках отсутствует**: колонки поступления в CSV нет, поэтому в
  статическом расчёте все аварии доступны с начала дня. Правило «авария доступна с момента
  поступления» реализовано и работает в сценарии перепланирования и при заданном `as_of`.
* **Ожидание в перерыв не видно в занятости.** Если окно клиента открывается сразу после
  обеда, инженер выезжает так, чтобы начать работу в первую же минуту окна, и может
  простоять у двери весь перерыв. В модели «в перерыв время не течёт», поэтому такое
  ожидание не попадает ни в `waiting_minutes`, ни в загрузку. Расписание при этом
  оптимально — выехать позже значит начать позже, — но по метрикам этот час невидим.
* **Отмена уже начатой работы не убирает её из плана** — только она, и только начатая.
  Отмена **до выезда** работает как обычно: заявка исчезает из плана целиком, маршрут
  перестраивается без заезда на неё. Но если инженер к моменту отмены уже выехал или
  работает, визит остаётся в маршруте как состоявшийся — с фактически отработанным
  временем, — и диспетчер получает предупреждение: иначе из маршрута пропадает точка, в
  которой человек физически стоит, и остаток дня строится от офиса. Такая — и только
  такая — отменённая заявка остаётся видна в назначениях: смысл события здесь «дальше не
  работаем», а не «этого не было». Граница та же, что и у заморозки вообще:
  `departure_at < event.at`.
* **`feasible_count` — не прогноз выполнимости**, а число назначенных заявок: план
  собирается только из допустимых назначений, отдельного прогноза у алгоритма нет. Поле
  выделено на будущее: когда появится источник фактов исполнения, «назначено» и «выполнено»
  разойдутся.
* **`constraints_valid` — не «план корректен»**, а внутренняя согласованность решения
  (расписания сходятся, дублей назначений нет). Единственный полный оракул корректности —
  `validate_plan`, он проверяет все инварианты § 9 независимо от планировщика.
* **Один день.** Многодневное планирование и перенос заявок на следующий день вне рамок.
