# openrouteservice для планировщика

Свой инстанс [openrouteservice](https://github.com/GIScience/openrouteservice) — источник
**расстояний по улицам**, **геометрии маршрутов** для карты и **поездок на общественном
транспорте по расписанию**. Лицензия GPL-3.0/LGPL-3.0,
данные OpenStreetMap, ключей API не требуется, наружу ничего не уходит.

Планировщик работает и без него — тогда расстояния считаются по координатам, а карта
рисует прямые. Подключение сервиса ничего не меняет в алгоритме: подменяется только
модель перемещения (`planner/ors.py`).

## Запуск

```bash
cd solution/deploy/ors
./download-osm.sh                 # выгрузка OSM: Центральный ФО, 877 МБ
docker compose up -d
docker compose logs -f            # первая сборка графов: ~12 мин + ~15 мин на транспорт
```

Готовность:

```bash
curl http://localhost:8080/ors/v2/health          # {"status":"ready"}
python ../../tools/ors_check.py                   # что умеет инстанс по каждому профилю
```

`tools/ors_check.py` печатает таблицу «способ передвижения → профиль → матрица → маршрут».
Это единственный достоверный способ узнать состав инстанса: собранные профили зависят
от конфигурации, а не от версии.

## Использование

```bash
cd solution
python demo.py --ors                              # расчёт на расстояниях по улицам
python viz/export.py --ors                        # выгрузка для карты с линиями маршрутов
python tools/ors_prefetch.py --with-geometry      # прогреть кэш и работать офлайн
python tools/ors_prefetch.py --transit            # ещё и расписания транспорта (разово)
python tools/ors_prefetch.py --transit --date 2026-09-21   # расписания на конкретный день
```

Раздел кэша расписаний включает дату отправления, поэтому план на другой день недели
в нём ничего не найдёт и уйдёт на расчёт по координатам — сказав об этом в `warnings`.
План на другую дату того же дня недели и часа переиспользует прогретый раздел как
приближение, тоже с пометкой. Подробности — в корневом `README.md`, раздел «Расписание
привязано к дате плана».

После `ors_prefetch.py` ответы сервиса лежат в `data/routing_cache.json`, и
`python demo.py` без флагов берёт расстояния оттуда — контейнер больше не нужен.
Смысл тот же, что у `data/geocache.json`: расчёт остаётся воспроизводимым и не зависит
от внешнего сервиса в момент показа.

## Что настроено в `ors-config.yml`

| Параметр | Значение | Почему |
|---|---|---|
| `endpoints.matrix.maximum_routes` | 25000 | ~100 точек на регион дают ~10 000 пар в одном запросе; дефолтных 2500 не хватает |
| `endpoints.isochrones.enabled` | false | изохроны задаче не нужны, а граф под них собирается отдельно |
| `…profile_default.service.maximum_waypoints` | 50 | в маршруте инженера редко больше 10 точек |
| `…profile_default.service.maximum_distance` | 500000 | дефолтные 100 км режут реальные маршруты: 349 км за смену (Москва — Кашира — Москва) |
| `…profile_default.service.maximum_snapping_radius` | 2000 | выровнен с `maximum_search_radius` матрицы; при дефолтных 400 м расстояние до неточно геокодированного адреса считалось, а линия до него не строилась |
| профили | `driving-car`, `foot-walking`, `cycling-regular`, `public-transport` | справочник ТЗ п. 2.4.1 целиком; у последнего берётся не матрица, а маршрут по расписанию, см. ниже |

Секцию под параметр надо выбирать аккуратно, ORS молча игнорирует ключ не на своём месте:

* лимиты **построения маршрута** (`maximum_distance`, `maximum_waypoints`,
  `maximum_snapping_radius`) читаются из `engine.profile_default.service`;
  в `endpoints.routing` они не работают;
* бюджет обхода графа для **матрицы** (`maximum_visited_nodes`) читается, наоборот, из
  `endpoints.matrix`. Одноимённый ключ в `profile_default.service` на матрицу не влияет —
  проверено замером: с ним и без него запрос отказывает на одном и том же размере блока,
  а снижение значения в `endpoints.matrix` ломает даже запрос из одного источника.

Полный список ключей лежит в самом контейнере:
`docker exec lct-ors sed -n '160,175p' /home/ors/config/example-ors-config.yml`.

Соответствие «способ передвижения ТЗ → профиль ORS» задано в
`planner/ors.py: DEFAULT_PROFILES` и покрыто тестом.

## Общественный транспорт

Профиль `public-transport` собран из GTFS-фида, который состоит из двух частей:
**наземный транспорт по настоящим расписаниям** портала data.mos.ru и **метро, МЦК и
МЦД по синтезированному тактовому расписанию**. Разница между частями принципиальна и
ниже не смазывается.

### Наземный транспорт: настоящие расписания

Портал отдаёт их шестью CSV, каждый со своим ключом. Состав ровно соответствует
минимальному GTFS, только разложен иначе:

| Выгрузка портала | Файл GTFS |
|---|---|
| `маршруты.csv` | `routes.txt` |
| `рейсы маршрутов.csv` | `trips.txt` |
| `расписание рейсов.csv` | `stop_times.txt` |
| `календарь маршрутов.csv` | `calendar.txt` |
| `остановки.csv` | `stops.txt` |
| `Транспортные предприятия.csv` | `agency.txt` |

```bash
python tools/osm_metro.py                  # разово: порядок станций -> data/метро.json
python tools/mosdata_to_gtfs.py            # data/*.csv -> deploy/ors/files/gtfs.zip
python tools/gtfs_check.py deploy/ors/files/gtfs.zip
```

Выгрузки между собой согласованы: у всех 203 791 рейса есть расписание и наоборот, все
1867 перечней дат на месте, календарь действует до 31.12.2030. Теряется 0.4 % рейсов —
215 ссылаются на отсутствующий маршрут, 679 на остановку без координат, 5 содержат
время, идущее назад по ходу движения. Итог наземной части: 933 маршрута, 202 892 рейса,
13 593 остановки, 5.3 млн строк расписания.

Весь архив вместе с рельсовой частью — 955 маршрутов, 225 254 рейса, 14 038 остановок,
5.78 млн строк расписания, 340 записей о пересадках, 35.7 МБ.

Конвертер ничего не досочиняет, кроме трёх помеченных в коде мест: вид транспорта
(нумерация портала совпадает с GTFS для автобуса и трамвая, но троллейбус у портала 5,
а в GTFS 11), пункт назначения рейса (в выгрузке пуст у всех рейсов, берётся из названия
маршрута — поле показывается пассажиру и на расчёт не влияет) и адрес сайта перевозчика
(GTFS требует непустой, заполнен только у Мосгортранса).

Отдельно про полночь: большая часть ночных рейсов в выгрузке уже записана как `24:55`
или `26:59` — ровно по соглашению GTFS. Но у 155 рейсов полночь записана обычным
`00:02`, и время «идёт назад»; конвертер переводит их на шкалу служебных суток. Отличить
это от ошибки можно по величине отката: прибавка суток даёт разрыв в считанные минуты,
а у настоящей ошибки он остаётся почти суточным.

### Метро, МЦК и МЦД: тактовое расписание

Расписаний рельсового транспорта Москвы в машиночитаемом виде **не существует**. На
портале есть справочник станций, выгрузка вестибюлей и рейтинг пассажиропотока — ни
одного времени отправления. Своего GTFS метрополитен не публикует.

Зато метро — ровно тот вид транспорта, который расписанием и не описывают: пассажир его
не знает и не смотрит, поезда идут с интервалом. Время поездки складывается из половины
интервала и хода по перегонам, и это моделируется честно. Все допущения собраны
константами в `tools/metro_gtfs.py`:

| Что | Значение | Откуда |
|---|---|---|
| Скорость перегона | метро 50, МЦК 48, МЦД 55 км/ч | подобрана так, чтобы со стоянкой дать публикуемую эксплуатационную |
| Стоянка на станции | метро 25 с, МЦК 30 с, МЦД 45 с | — |
| Проверка | 1.72 км среднего перегона → 124 с хода + 25 с стоянки = 41.5 км/ч эксплуатационной | метрополитен публикует 41.6 км/ч |
| Интервал, метро | 2.5 мин в пик, 4 мин в межпик, 6 мин на краях суток | данные метрополитена |
| Интервал, МЦК / МЦД | 4 и 8 мин / 6 и 15 мин | — |
| Часы работы | 05:30–01:00 (МЦД до 00:30) | — |
| Пересадка между линиями | решает расстояние: ≤400 м при совпадении названия — 3 мин, ≤350 м при разных названиях — 5 мин, ≤1 км при совпадении названия — пешком по расстоянию, дальше записи нет | `transfers.txt` |

Две вещи взяты не из головы:

* **порядок станций на линии** — из OSM (`tools/osm_metro.py`, отношения `type=route`).
  У портала его нет вовсе: у старых линий он случайно совпадает с кодом станции
  (86…109 — Калужско-Рижская), у Большой кольцевой коды идут 230, 238, 242, 298, 307,
  312… — станции попадали в справочник по мере открытия. Восстановить порядок геометрией
  тоже нельзя: два кольца и ветка Филёвской ломают любую сортировку «вдоль линии»;
* **координата станции** — центроид её вестибюлей из выгрузки «Входы и выходы вестибюлей
  станций метро.csv». Не платформа: в маршруте важно место, куда человек приходит с
  улицы, — именно до координаты остановки сервис считает подход по уличному графу.
  Сличение идёт по паре «линия + станция», и это не перестраховка: «Дубровка» есть на
  Люблинско-Дмитровской и на МЦК, «Новогиреево» — на восьмой линии и на МЦД-4. По одному
  названию три десятка платформ уехали бы к чужим вестибюлям — молча, потому что
  координата всё равно остаётся правдоподобной; у МЦД-2 «Люблино» ошибка была 2 км.
  Все 17 линий выгрузки совпадают по названию с линиями в OSM, так что ключ сходится
  без исключений.

Результат: 22 линии (16 метро + МЦК + МЦД-1…4), 445 остановок, 22 362 рейса,
478 тысяч строк расписания, 170 пар станций с пересадкой. Все 260 действующих станций
из справочника портала в фиде есть — это проверяет сам сборщик и печатает в отчёте.

Три места, где модель отступает от наивной:

* **кольцевой рейс проезжает круг дважды.** Круг в GTFS задаётся рейсом, который
  начинается и кончается на одной станции, но рейс — это цепочка «сел не раньше, вышел
  не позже», и пассажиру, севшему у её конца, начало недоступно. На Кольцевой это каждая
  десятая пара станций. Настоящий поезд кольца конечной не имеет, поэтому цепочка
  продлевается на второй круг;
* **ответвление не заводит своих платформ.** Филёвская 4А идёт теми же станциями, что и
  4, до «Киевской». Дай ей собственные остановки — те же платформы удвоятся, а между их
  половинами появится трёхминутная пересадка из ничего;
* **пересадку задаёт расстояние, а не совпадение названия.** Правило «то же имя — 180
  секунд» выглядит очевидным и в московской сети неверно: «Перово» восьмой линии и
  «Перово» МЦД-3 стоят в 2.2 км друг от друга, «Люблино» десятой и МЦД-2 — в 2.0 км.
  Пассажир идёт туда двадцать минут поверху, а запись в `transfers.txt` дарила ему их
  обе. Дарёные минуты опаснее отсутствующей пересадки: маршрутизатор выбирает по времени
  и охотно строит поездку через переход, которого нет. Поэтому имя только смягчает
  порог: до 400 м — узел (3 мин, проверено по данным: из 123 одноимённых пар 114
  укладываются в 500 м, а самые длинные настоящие переходы узла — «ЗИЛ» МЦК ↔ БКЛ 470 м
  и «Дубровка» 10 ↔ 14 630 м), до километра — пешком по расстоянию (4.5 км/ч с
  коэффициентом извилистости 1.3), дальше записи нет вовсе. Отсутствие записи не
  запрещает пересадку: без неё маршрутизатор ищет путь между платформами по уличному
  графу и считает его честно.

### Что этот фид даёт

**Матрицу он не чинит, и починить её нечем.** У `/v2/matrix` нет параметра времени
отправления, поэтому расписания в неё не попадают: ORS отвечает пешей доступностью.
Замер на паре Медведково — Ясенево: матрица 428 мин, пешком 427 мин. Внешне ответ
выглядит рабочим, и это опаснее отказа. Отбор задан в `planner/ors.py:
NO_MATRIX_PROFILES`, `tools/ors_check.py` помечает такую матрицу словом «пешком!».

**Маршрут по расписанию он даёт.** `/v2/directions` время отправления принимает, и
планировщик считает общественный транспорт именно им — по одной паре точек за запрос
(`planner/ors.py: fetch_transit_legs`). Та же пара Медведково — Ясенево:

```
выезд в 10:00, в пути 63 мин, одна пересадка
   пешком 4 мин (354 м)
   [автобус] 601   10:05→10:10  МФЦ Северное Медведково → Метро «Медведково» (3 ост.)
   пешком 1 мин (96 м)
   [метро]   6     10:12→11:02  Медведково → Ясенево (22 ост.)
   пешком 0 мин (26 м)
```

Тот же маршрут до добавления метро занимал 151 минуту шестью рейсами наземного
транспорта. Ещё замеры на 10:00: Выхино — Щёлковская 41 минута (МЦД-3 +
Арбатско-Покровская), Москва-Сити — Комсомольская 27 минут (Филёвская +
Сокольническая).

Состав поездки доезжает до плана (`Visit.transit`), а не остаётся внутри сервиса:
диспетчеру нужно не «в пути 63 минуты», а на чём ехать и где садиться.

Здесь важен один параметр. По умолчанию ORS разрешает идти пешком до остановки не
больше 15 минут, и с этим дефолтом часть участков не строится вовсе: сервис отвечает
`PT entry and exit points found but no connecting route` и прямо советует увеличить
время. `planner/ors.py: PT_WALKING_TIME` поднимает его до 30 минут; с 60 результат тот
же, то есть 30 уже достаточно.

### Чего не хватает: область

Фид покрывает Москву, ТиНАО и коридоры МЦД. Из 277 адресов выгрузок часть — Кашира,
Ступино, часть Домодедова — лежит в 60–70 км от ближайшей обслуживаемой остановки.

Это не ломает расчёт: пару, которую сервис не связал, планировщик считает по координатам
и пишет об этом в `warnings`. Но областной фид нужен, и его нет: набор «Смежные маршруты
пассажирских перевозок» на том же портале содержит 267 маршрутов Мострансавто с трассами,
однако **без единого времени** — это выгрузка трасс, а не расписаний. Машиночитаемых
расписаний Мострансавто не публикует.

### Как включить профиль

Блок `public-transport` в `ors-config.yml` уже раскомментирован. После замены фида:

```bash
docker compose down && rm -rf ors-docker/graphs/public-transport && docker compose up -d
```

Удалять весь каталог `graphs` не нужно — графы лежат по профилям, и остальные три
переживут пересборку. Сборка графа общественного транспорта из ЦФО плюс импорт фида
занимает около 15 минут (было 11 до рельсовой части). Дальше:

```bash
python tools/ors_check.py                  # колонка «маршрут» покажет номера маршрутов
python tools/ors_prefetch.py --transit     # разовый прогрев расписаний в кэш
```

В логе сборки встречается `routes line 215: Number 11.0 outside of acceptable range
[0.0,7.0]` — это валидатор conveyal ругается на троллейбус: код 11 задан спецификацией
GTFS, а его таблица кодов старше. На загрузку фида это не влияет и было до рельсовой
части.

Если инстанс не ответит на этот профиль, планировщик останется на расчёте по
координатам: без ошибок, без правок кода и с предупреждением в плане.

## Ресурсы

| | ЦФО (`central`) | Москва (`moscow`) |
|---|---|---|
| Размер выгрузки | 877 МБ | ~85 МБ |
| Сборка графов (3 профиля) | ~12 мин | 3-5 мин |
| + граф общественного транспорта | ~15 мин | не замерялось |
| Память (`XMX`) | 10 ГБ | 4 ГБ |
| Покрытие данных | Москва и область целиком | Москва без дальнего Подмосковья |

Замеры — с фактического прогона на 22 ядрах и 16 ГБ; профили собираются параллельно
(`ors.engine.init_threads: 3`). Граф общественного транспорта замерен отдельно: он
добавлялся к уже собранному инстансу, поэтому сколько займёт сборка всех четырёх сразу —
не проверено; `init_threads` при этом стоит поднять до 4, иначе четвёртый профиль
дождётся освободившегося потока.

Адреса выгрузок лежат в диапазоне 54.84–55.78 с.ш. и 37.54–38.97 в.д. — это и Кашира,
и Егорьевск, а не только Москва. С выгрузкой `moscow` такие точки не лягут на граф:
ORS вернёт для них `null`, и эти пары посчитаются по координатам. Для полного прогона
нужен `central`.

Прогрев кэша по всем трём наборам (`tools/ors_prefetch.py --with-geometry`) занимает
десятки минут, и почти всё это время — пеший и велосипедный профили: они считают
матрицу перебором. Автомобильная матрица на 66 точках отвечает за секунды.

## Если что-то пошло не так

* **`Unable to connect` / таймауты** — контейнер ещё собирает графы; смотрите
  `docker compose logs -f`, при первом запуске это норма.
* **`HTTP 404` на профиле** — профиль не собран; включите его в `ors-config.yml`,
  выставьте `REBUILD_GRAPHS: True` и перезапустите.
* **Правки в `ors-config.yml` не подействовали** — если менялось что-то, влияющее на
  граф (профили, `preparation`, `elevation`, выгрузка OSM), графы нужно пересобрать.
  `REBUILD_GRAPHS=True docker compose up` не поможет: значение из секции `environment`
  в compose перекрывает переменную окружения. Надёжный способ — удалить графы:

  ```bash
  docker compose down && rm -rf ors-docker/graphs && docker compose up -d
  ```
* **`Search exceeds the limit of visited nodes` на матрице для `foot-walking` или
  `cycling-regular`** — эти профили считают матрицу перебором, и бюджет обхода графа
  тратится на запрос целиком: на инстансе со стандартным лимитом пеший запрос ломается
  уже на нескольких десятках точек. Планировщик это переживает сам — `fetch_matrix`
  делит блок пополам и повторяет, пока запрос не пройдёт. Поднятый
  `maximum_visited_nodes` в `ors-config.yml` просто позволяет обойтись меньшим числом
  запросов. Включение contraction hierarchies для этих профилей проверялось и на
  поведение матрицы не повлияло — 20 минут сборки графа тратятся впустую.
* **`Could not find routable point within a radius of N meters`** — адрес геокодирован
  неточно (уровень улицы или населённого пункта) и рядом с координатой нет дороги в OSM.
  Ломается геометрия **всего** маршрута, а не одного участка. Лечится в первую очередь
  правкой координаты в `data/geocache.json`; `maximum_snapping_radius` — только страховка,
  он привязывает точку к далёкой дороге и тем самым маскирует ошибку геокодирования.
* **`The approximated route distance must not be greater than N meters`** — маршрут длиннее
  `maximum_distance`. Поднимается в `profile_default.service`, пересборка графов не нужна,
  достаточно `docker compose restart` (~30 секунд).
* **`maximum_routes exceeded`** — поднимите лимит в конфиге либо запустите
  `tools/ors_prefetch.py --max-routes 2500`: планировщик нарежет матрицу на блоки.
* **Прокси** — если в окружении задан `HTTP_PROXY`, добавьте адрес инстанса в `NO_PROXY`,
  иначе запросы к localhost уйдут через прокси.
