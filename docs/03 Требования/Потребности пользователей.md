# Потребности пользователей

Требования сгруппированы по смыслу и расположены по ходу работы с заявкой. В каждой группе одна таблица со строками-разделителями по приоритетам MoSCoW. Заголовок и описание группы задают общий контекст для ее требований.

В матрицу включены атомарные требования с конкретной бизнес-ценностью: сокращение ручной работы и затрат, соблюдение сроков, предотвращение невыполнимых назначений или сокращение числа необслуженных заявок. Для информационных требований указано, какое рабочее решение позволяет принять информация. Польза описывает ожидаемый эффект, а не подтвержденный результат внедрения.

Приоритеты: **Must have** - обязательные, **Should have** - важные дополнительные, **Could have** - при наличии времени.

## Распределение заявок

Статическое распределение выездных работ на один день. При нехватке ресурсов учитывается порядок авария → подключение → ремонт / дозаказ. Объем работ и число инженеров остаются показателями качества; время перемещения важнее пробега.

Таблица 2. Распределение заявок

| Как | Я хочу | Чтобы |
|---|---|---|
| **Must have** | | |
| диспетчер | назначать на каждую заявку одного инженера | распределить персональную ответственность за выезд |
| диспетчер | назначать инженеров только в их регионе | соблюдать территориальное закрепление |
| диспетчер | назначать заявки только инженерам с нужным навыком | исключить работы, к которым исполнитель не допущен |
| диспетчер | распределять заявки с приоритетом аварий, затем подключений, затем ремонтов и дозаказов | сохранить обслуживание более важных работ при нехватке ресурсов |
| диспетчер | учитывать требуемый транспорт, если он задан | обеспечить выполнение требования заявки |
| диспетчер | соблюдать согласованное окно прибытия | обеспечить выезд в согласованный с клиентом интервал |
| диспетчер | учитывать длительность обслуживания | исключить пересечение работ в расписании |
| диспетчер | учитывать продолжительность смены | планировать выезды в рабочее время |
| диспетчер | учитывать полное время перемещения | учесть дорогу и сопутствующие затраты времени |
| диспетчер | автоматически распределять заявки | сократить время подготовки плана |
| диспетчер | максимизировать число выполнимых заявок | выполнить за день больше работ |
| диспетчер | сокращать число исполнителей при сохранении выполненного объема | снизить потребность в персонале |
| диспетчер | отдавать предпочтение более быстрому перемещению при прочих равных | высвободить время для обслуживания |
| диспетчер | учитывать пробег после более важных критериев | сократить лишние перемещения |
| **Could have** | | |
| диспетчер | учитывать оборудование, выданное инженеру на день | исключить выезд без необходимого роутера или приставки |
| диспетчер | учитывать дополнительные уровни квалификации | различать подготовку инженеров с одним навыком |

Дополнительные уровни квалификации и объем запаса оборудования определяет команда. При перепланировании время визита можно скорректировать, коммуникацию с клиентом ведет поддержка. Расчет соблюдает актуальные временные ограничения. Неназначение не отменяет заявку автоматически.

## Плановые показатели

Сравнение выполненного объема, числа исполнителей и затрат времени. Плановые значения отделены от фактов.

Таблица 6. Показатели и сравнение

| Как | Я хочу | Чтобы |
|---|---|---|
| **Must have** | | |
| диспетчер | видеть прогноз выполнимых и число неназначенных заявок | оценить охват работ на день |
| диспетчер | видеть число задействованных инженеров | оценить потребность в персонале |
| диспетчер | сравнивать базовый и рассчитанный планы по выполнимым заявкам и числу инженеров | выбрать вариант с большим объемом работ и меньшей потребностью в персонале |
| диспетчер | сравнивать время перемещения | оценить затраты рабочего времени |
| диспетчер | видеть суммарный пробег и пробег инженеров | проверить лишние перемещения |
| **Should have** | | |
| диспетчер | сравнивать несколько вариантов плана | выбрать подходящий вариант при сопоставимом объеме работ |
| диспетчер | фиксировать завершение и отмену по информации исполнителя | сохранять фактическое состояние заявок |
| диспетчер | видеть подтвержденные факты выполнения отдельно от назначений | оценить результат рабочего дня |

Базовый алгоритм назначает заявки по порядку поступления первому подходящему инженеру по порядку входа. Сравнение проводится на одинаковых исходных данных. Контрольная выгрузка не является эталоном и не задает обязательное число исполнителей. Назначенная заявка не равна выполненной. Значение отмены в метрике выполненных требует уточнения формулировки экспертов, см. [[Открытые вопросы]].

## Перераспределение заявок

Дополнительный сценарий после статического расчета. Он учитывает новые аварии, подтвержденные факты, актуальное время визитов и остаток оборудования.

Таблица 7. Перераспределение заявок

| Как | Я хочу | Чтобы |
|---|---|---|
| **Should have** | | |
| диспетчер | перестраивать остаток дня после поступления аварии | включить приоритетную работу в расписание |
| диспетчер | исключать закрытые заявки из нового планирования | сохранять выполненную работу и не назначать ее повторно |
| диспетчер | переназначать еще не начатые работы | использовать доступные ресурсы |
| диспетчер | учитывать доступный остаток оборудования при пересчете | назначать обеспеченные оборудованием работы |
| диспетчер | корректировать время визита с передачей изменений поддержке | обеспечить коммуникацию с клиентом |
| диспетчер | пересчитывать остаток плана после отмены или недоступности инженера | использовать освободившееся время и перераспределить работы |
| **Could have** | | |
| диспетчер | видеть влияние новой заявки на назначения, порядок и маршруты | оценить последствия перераспределения |

По ответу экспертов № 9 динамический сценарий не обязателен для хакатона. При его реализации сохраняются факты закрытия и прошлые планы. Правила фиксации незавершенных работ и передачи изменений поддержке перечислены в [[План изменений по ответам экспертов]].

## Основания приоритетов

Потребности Should have помогают диспетчеру управлять рабочим днем после реализации обязательного сценария.

Потребности Could have улучшают качество решений, но не нужны для завершения обязательной демонстрации.

## Граница демонстрации

Для обязательной демонстрации достаточно статического расчета расписания по исходной выгрузке на один день. Место размещения не ограничено. Предоставленный набор использует московское время. Перерывы и поддержка других часовых поясов России относятся к Could have.

Для общественного транспорта допустима усредненная оценка времени или скорости. Реальные и комбинированные маршруты - Could have.
