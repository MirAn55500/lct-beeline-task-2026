# Правила модели

## Границы описания

Модель включает 6 основных сущностей, маршрут как составную часть плана и 3 справочника. Навыки и способы передвижения заданы фиксированными списками, загрузка данных описана как операция со служебной записью результата. Полный состав и переходы к отдельным заметкам находятся в [[docs/01 Навигация/01 Навигация]]. Технические имена, примеры и обязательность полей предложены для реализации; они не являются готовым контрактом API. Неопределенные интеграции отмечены в заметках.

## Согласованные решения

- Пользователи-исполнители имеют профиль, навыки, транспорт и точку старта.
- Транспорт определяет профиль маршрутного API. Время в пути и расстояние поступают из API.
- Способ передвижения задается у инженера. Если в заявке указан требуемый транспорт, при назначении проверяется совпадение. Ранее записанное исключение этого ограничения не подтверждено и отменено.
- Бригада и подразделение - одна сущность. Бригада задает районы работы и основной график; инженер может корректировать наследуемые значения.
- Роль инженера задает навыки и снаряжение. Индивидуальные корректировки инженера имеют приоритет над ролью.
- Для корректировок наборов предложены добавление и исключение отдельных элементов; удаление корректировки возвращает наследование.
- Индивидуальное изменение имеет приоритет над основным графиком.
- Начало работы входит во временное окно, путь и вся работа укладываются в рабочее время.
- Маршрут начинается в точке старта сотрудника. Обратный путь после последней заявки не требуется.
- Критерии: выполнить заявки с учетом срочности, сократить число сотрудников, затем пробег.
- План должен объяснять назначения и неназначения. Математический оптимум доказывать не требуется.

## Как читать источник атрибута

В таблицах сущностей колонка «Описание параметра» включает происхождение значения в проектируемом сервисе; в таблицах исходных данных источник указан отдельно. Она не утверждает, что интеграции уже реализованы.

- **Из выгрузки**: значение есть в предоставленном CSV. Указана точная колонка или служебная строка. Преобразование формата даты при загрузке не меняет первичный источник.
- **При загрузке**: система создает значение в процессе загрузки, берет его из параметров загрузки либо сопоставляет строку со справочником. В самом CSV готового значения нет.
- **Пользователь**: человек вводит или выбирает значение в указанной карточке, справочнике или настройках.
- **Автоматически**: система создает значение, копирует его из указанного поля, вычисляет по формуле или получает из названного API.

Если способов несколько, в ячейке указано условие каждого: загрузка, ручное создание или последующее уточнение. Для еще не выбранного источника стоит явная отметка. Пустота не подменяется вымышленным источником или значением.

Атрибуты каждой сущности оформляются одной таблицей. Смысловые группы выделяются строками-сегментами внутри таблицы. Вложенные поля с `[]` описывают элементы списка внутри сущности и не требуют отдельной заметки.

## Общие типы

- ID хранится строкой. У каждой сущности собственный уникальный ключ.
- Дата и время: ISO 8601 с часовым смещением. Календарная дата: YYYY-MM-DD. Время графика: HH:MM.
- Время работ и емкость: минуты. Время API может быть дробным. Округление для интерфейса не меняет значения проверки ограничений.
- Расстояния: километры. Отображение округляется отдельно от расчета.
- Координаты: WGS84. В отдельных полях latitude/longitude, в GeoJSON порядок longitude, latitude.
- В таблицах сущностей `+` означает обязательность. `-` означает необязательность или условие из примечания. «До расчета» требует дозаполнения перед оптимизацией; «Расчет» обозначает вычисляемое поле.
- Пустое значение означает отсутствие или неизвестность. Оно не заменяется нулем автоматически.
- Связи задаются через ID. В заметках используются ссылки на определения сущностей.

## Рабочее время

Емкость дня = сумма рабочих интервалов. Перерывы заданы разрывами между интервалами. Предложенная модель использует интервалы внутри одного календарного дня.

Занятость = работа + перемещения + ожидание внутри рабочих интервалов. Свободное время = емкость - занятость. Разрывы рабочего времени в занятость не входят.

Пример: 09:00-13:00 и 14:00-18:00 дают 480 минут. Индивидуальный день 10:00-14:00 заменяет основной и дает 240 минут.

## Открытые решения

- Районы строго ограничивают назначения или дают предпочтение при выборе инженера.

- Поставщик маршрутного API, поддержка всех четырех способов передвижения и времени отправления.
- Источник координат для адресов: выбранный API или отдельное геокодирование.
- Соответствие типов BK/HD навыкам и видам работ, нормативная длительность.
- Источник статусов, их словарь, ID событий и порядок обновления.
- Правила фиксации работ в пути и в процессе, координаты сотрудников и время освобождения при перепланировании.
- Точное разрешение конфликта срочности и общего числа выполненных заявок при дефиците ресурсов. Предложение записано в [[Правила модели#Правила расчета|правилах расчета]].

## Основания

- [ТЗ Билайн Бизнес](../../../Техническое%20задание.pdf), обязательные ограничения и формат результата.
- Уточнения пользователя в задаче: транспорт через API, оргструктура и индивидуальный рабочий день, потребность в статусах выполнения.
- [Обзор моделей TRSP](https://link.springer.com/article/10.1007/s00291-026-00865-y): математическая основа распределения и маршрутизации. Конкретный алгоритм сервиса пока не реализован.

## Планы и пересчет

Каждый вариант расчета хранится как отдельный [[План работы]]. Статус плана определяет его применение, состояние расчета хранится отдельно. Новый план ссылается на предыдущий через `previous_plan_id`; до подтверждения нового продолжает действовать прежний. После подтверждения прежний архивируется. Назначения и маршруты ссылаются на план через `plan_id`.

## Связи в YAML

«Раздел» содержит ссылку на раздел карты, «Связи» - список связанных сущностей с короткими названиями. Список показывает связи типов, а не количество объектов. Количество, обязательность и назначение связи задаются в описании полей ID. Обратные коллекции определяются по ссылкам дочерних объектов.

## Состав модели

- Основные сущности: [[Заявка на работу]], [[План работы]], [[Назначение на работу]], [[Инженер]], [[Бригада]], [[Роль инженера]].
- Составная часть плана: [[Маршрут инженера]]. Сохраняет собственные данные и связи, открывается внутри плана.
- Управляемые справочники: [[Вид работ]], [[Район работы]], [[Снаряжение]].
- Фиксированные списки: [[Навык]], [[Способ передвижения]]. Пользователь выбирает значения в рабочих карточках, состав списков задан системой.
- Операция: [[Загрузка данных]]. Техническая запись результата сохраняет происхождение записей и ошибки обработки.

Типы заметок в YAML: `entity`, `component`, `dictionary`, `enumeration`, `operation` соответственно. Отдельная заметка описывает понятие и сама по себе не означает отдельный экран сервиса.

## Правила расчета

- Проверки навыка, требуемого транспорта и снаряжения, временного окна и рабочего времени выполняются системой. Правило территорий остается открытым решением.
- Предлагаемый порядок критериев: `urgent_unassigned`, `unassigned`, `used_engineers`, `distance_km`. Он дает срочным заявкам преимущество при дефиците ресурсов и еще требует подтверждения. После согласования порядок закладывается в алгоритм; редактор критериев для диспетчера не предусмотрен.
- Базовый алгоритм берет заявки в порядке поступления и назначает первому подходящему инженеру по порядку входа. Заявки маршрута следуют порядку назначения.
- Истечение лимита поиска не доказывает невозможность решения.

## Техническая конфигурация

Конфигурация задается при развертывании приложения. Пользовательские параметры конкретного плана - дата, выбранные заявки и инженеры - описаны в [[План работы|плане работы]].

- `timezone` - часовой пояс приложения, сохраняемый в плане.
- `search_time_limit_seconds` - положительный лимит поиска в секундах, определяется после замеров.
- `routing.provider`, `routing.base_url`, `routing.credential_ref` - поставщик, адрес API и ссылка на ключ доступа. Сам ключ хранится в защищенной конфигурации, а не в заметках или снимке плана.
- `routing.transport_profiles` - соответствие четырех кодов способов передвижения профилям выбранного API. Замена недоступного способа другим не допускается.
- `routing.supports_departure_time` - подтвержденная возможность API учитывать время отправления.
- `geocoding.provider` - сервис преобразования адресов в координаты, может совпадать с маршрутным сервисом. Поставщики пока не выбраны.

План автоматически сохраняет `settings_snapshot` с примененными правилами и конфигурацией, необходимой для воспроизведения расчета. Отдельной сущности и экрана «Параметры расчета» нет.

## Получение маршрутов и статусов

- Алгоритм отправляет маршрутному API пары координат, способ передвижения и, если поддерживается, время отправления. Участки проверяются на плановое время; время туда и обратно может различаться.
- Отсутствие маршрута и ошибка API различаются; ошибка не заменяется нулевым временем.
- Для источника статусов нужно определить способ получения, ключ заявки, время факта, словарь статусов и обработку повторных или запоздавших сообщений. Ручной режим для демо остается вариантом. Параметры webhook, опроса и доступа уточняются после выбора источника.
