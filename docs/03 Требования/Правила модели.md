# Правила модели

## Границы описания

Модель включает 6 основных сущностей, маршрут как составную часть плана и 3 справочника. Навыки задаются списком типов работ без ограничения тремя значениями, способы передвижения - списком поддерживаемых профилей, загрузка данных описана как операция со служебной записью результата. Полный состав и переходы к отдельным заметкам находятся в [[01 Навигация/01 Навигация]]. Технические имена, примеры и обязательность полей предложены для реализации; они не являются готовым контрактом API. Неопределенные интеграции отмечены в заметках.

## Согласованные решения

- Бригада сервиса объединяет инженеров и задает регион, офис старта и основной график. Продолжительность рабочего дня вычисляется по рабочим интервалам. Инженер может иметь индивидуальное изменение дня.
- В исходной колонке «Бригада» указан отдельный инженер. Это значение не создает бригаду сервиса. Каждая заявка выполняется одним человеком и требует выезда.
- Инженер наследует регион и стартовый офис от бригады. Межрегиональные назначения запрещены. Первоначальный маршрут дня начинается в офисе своего региона.
- Навык определяет доступные типы заявок. Число навыков не ограничено, квалификация задается отдельно по каждому навыку и дополняется синтетически. Правило ее влияния на распределение остается открытым.
- Транспорт независим от навыков. У инженера свой способ передвижения. Если заявка отдельно требует способ передвижения, проверяется совместимость.
- Время перемещения включает парковку, подъем и прочие сопутствующие затраты. Геокодирование разрешено сторонними сервисами, предпочтительно с открытым исходным кодом.
- Колонки «Начало» и «Окончание» задают окно прибытия. Работа не начинается раньше окна. Прибытие позже начала, но внутри окна допустимо. Окна не сдвигаются.
- Расчет выполняется в рамках одного дня, для предоставленного набора используется Europe/Moscow. Работа и перемещения учитываются в рабочем времени.
- Автоматическая отмена заявок запрещена. Статус «Отменена» в источнике означает отказ клиента после прибытия инженера.
- Переназначение заявок допустимо. Границы фиксации начатых работ уточняются отдельно.
- Первый показатель качества - количество выполненных заявок, второй - сокращение числа исполнителей. Приоритетность и время перемещения важнее пробега. Полный порядок разрешения конфликтов критериев требует уточнения.
- Объяснения нужны для неназначений и проблем при перераспределении. Объяснять каждое успешное назначение и каждый маршрут не требуется.
- Оборудование: роутер или приставка, выдача в начале дня. Потребность не определяется типом подключения.
- Допустимость overbooking подтверждена, его точный смысл не определен. Это не готовое разрешение нарушать окна или назначать человеку одновременно две работы.

## Как читать источник атрибута

В таблицах сущностей колонка «Описание параметра» включает происхождение значения в проектируемом сервисе; в таблицах исходных данных источник указан отдельно. Она не утверждает, что интеграции уже реализованы.

- **Из выгрузки**: значение есть в предоставленном CSV. Указана точная колонка или служебная строка. Преобразование формата даты при загрузке не меняет первичный источник.
- **При загрузке**: система создает значение в процессе загрузки, берет его из параметров загрузки либо сопоставляет строку со справочником. В самом CSV готового значения нет.
- **Пользователь**: человек вводит или выбирает значение в указанной карточке, справочнике или настройках.
- **Автоматически**: система создает значение, копирует его из указанного поля, вычисляет по формуле или получает из названного API.

Если способов несколько, в ячейке указано условие каждого: загрузка, ручное создание или последующее уточнение. Для еще не выбранного источника стоит явная отметка. Пустота не подменяется вымышленным источником или значением.

Атрибуты каждой сущности оформляются одной таблицей. Смысловые группы выделяются строками-сегментами внутри таблицы. Вложенные поля с `[]` описывают элементы списка внутри сущности и не требуют отдельной заметки.

## Общие типы

- ID хранится строкой. У каждой сущности собственный уникальный ключ.
- Дата и время: ISO 8601 с часовым смещением. Календарная дата: YYYY-MM-DD. Время графика: HH:MM.
- Время работ и емкость: минуты. Время API может быть дробным. Округление для интерфейса не меняет значения проверки ограничений.
- Расстояния: километры. Отображение округляется отдельно от расчета.
- Координаты: WGS84. В отдельных полях latitude/longitude, в GeoJSON порядок longitude, latitude.
- В таблицах сущностей `+` означает обязательность. `-` означает необязательность или условие из примечания. «До расчета» требует дозаполнения перед оптимизацией; «Расчет» обозначает вычисляемое поле.
- Пустое значение означает отсутствие или неизвестность. Оно не заменяется нулем автоматически.
- Связи задаются через ID. В заметках используются ссылки на определения сущностей.

## Рабочее время

Емкость дня - сумма рабочих интервалов инженера на дату плана. Основные интервалы задаются в бригаде, индивидуальное изменение дня заменяет их целиком.

Занятость = обслуживание + перемещения + ожидание в рабочее время. Свободное время = емкость - занятость. Дорога учитывается один раз: норматив обслуживания берется без дорожной составляющей, см. [[Нормативы работ]].

Для окна 10:00-12:00 прибытие в 09:50 означает ожидание до 10:00, прибытие в 11:00 допустимо. Прибытие после 12:00 не считается попаданием в окно. Распространение верхней границы на начало обслуживания еще уточняется.

Перерывы - дополнительная возможность, задаваемая разрывами интервалов. В обязательном сценарии достаточно одного рабочего интервала на день. Модель не использует индивидуальную скорость инженера или возможность договориться о раннем начале.

Список неуточненных правил ведется в [[Открытые вопросы]]. Там же указаны зависимости расчета: квалификация, overbooking, граница окна, критерии, оборудование и получение фактов выполнения.

## Основания

- [ТЗ Билайн Бизнес](../../../Техническое%20задание.pdf), обязательные ограничения и формат результата.
- Ответы сессии и уточнения пользователя от 17.09.2026: одна заявка на одного инженера, сохранение бригады сервиса, офис и график бригады, интерпретация исходной колонки «Бригада», ограничения и показатели расчета.
- [Обзор моделей TRSP](https://link.springer.com/article/10.1007/s00291-026-00865-y): математическая основа распределения и маршрутизации. Конкретный алгоритм сервиса пока не реализован.

## Планы и пересчет

Каждый вариант расчета хранится как отдельный [[План работы]]. Статус плана определяет его применение, состояние расчета хранится отдельно. Новый план ссылается на предыдущий через `previous_plan_id`; до подтверждения нового продолжает действовать прежний. После подтверждения прежний архивируется. Назначения и маршруты ссылаются на план через `plan_id`.

## Связи в YAML

`section` содержит ссылку на раздел карты, `related` - список связанных заметок. Ключи YAML записываются на английском. Количество и обязательность объектов связи описываются в полях ID. Обратные коллекции определяются по ссылкам дочерних объектов. Навигационные связи не дублируются отдельными строками в тексте.

## Состав модели

- Основные сущности: [[Заявка на работу]], [[План работы]], [[Назначение на работу]], [[Инженер]], [[Бригада]], [[Роль инженера]].
- Составная часть плана: [[Маршрут инженера]]. Сохраняет собственные данные и связи, открывается внутри плана.
- Управляемые справочники: [[Вид работ]], [[Район работы]], [[Снаряжение]].
- Списки значений: [[Навык]], [[Способ передвижения]]. Пользователь выбирает значения в карточках. Коды навыков определяются по типам работ набора, способы передвижения - по поддерживаемым профилям.
- Операция: [[Загрузка данных]]. Техническая запись результата сохраняет происхождение записей и ошибки обработки.

Типы заметок в YAML: `entity`, `component`, `dictionary`, `enumeration`, `operation` соответственно. Отдельная заметка описывает понятие и сама по себе не означает отдельный экран сервиса.

## Правила расчета

- Проверяются регион, навык, явно заданный транспорт, оборудование при его учете, окно прибытия и рабочее время. Проверка уровня квалификации вводится после определения шкалы и правила влияния.
- Качество оценивается прежде всего выполненными заявками, затем числом задействованных инженеров. До исполнения доступен прогноз выполнимости, а не факт выполнения. Приоритетность и время пути выше пробега. Веса и полный порядок критериев пока не заданы, см. [[Открытые вопросы]].
- Базовый алгоритм берет заявки в порядке поступления и назначает первому подходящему инженеру по порядку входа. Порядок посещения совпадает с порядком назначения.
- Контрольное распределение не является эталоном качества или обязательной численности. Базовый и оптимизированный алгоритмы сравниваются на одинаковых входах.
- Overbooking требует отдельного определения допустимости и показателей. До согласования конфликтный план нельзя объявлять выполнимым только потому, что всем заявкам назначены исполнители.
- Истечение лимита поиска не доказывает невозможность решения. Неназначение не меняет статус заявки на «Отменена».

## Техническая конфигурация

Конфигурация задается при развертывании приложения. Пользовательские параметры конкретного плана - дата, выбранные заявки и инженеры - описаны в [[План работы|плане работы]].

- `timezone` - Europe/Moscow для предоставленного набора, сохраняется в плане. Поддержка других региональных поясов - дополнительная возможность.
- `search_time_limit_seconds` - положительный лимит поиска в секундах, определяется после замеров.
- `routing.provider`, `routing.base_url`, `routing.credential_ref` - поставщик, адрес API и ссылка на ключ доступа. Сам ключ хранится в защищенной конфигурации, а не в заметках или снимке плана.
- `routing.transport_profiles` - соответствие четырех кодов способов передвижения профилям выбранного API. Замена недоступного способа другим не допускается.
- `routing.supports_departure_time` - подтвержденная возможность API учитывать время отправления.
- `geocoding.provider` - сервис преобразования адресов в координаты, может совпадать с маршрутным сервисом. Поставщики пока не выбраны.

План автоматически сохраняет `settings_snapshot` с примененными правилами и конфигурацией, необходимой для воспроизведения расчета. Отдельной сущности и экрана «Параметры расчета» нет.

## Получение маршрутов и статусов

- Алгоритм отправляет маршрутному API пары координат, способ передвижения и, если поддерживается, время отправления. Время туда и обратно может различаться. Итоговая оценка перемещения включает сопутствующие затраты. Источник этих затрат нужно определить, если API их не учитывает.
- Отсутствие маршрута и ошибка API различаются; ошибка не заменяется нулевым временем.
- Для источника статусов нужно определить способ получения, ключ заявки, время факта, словарь статусов и обработку повторных или запоздавших сообщений. Ручной режим для демо остается вариантом. Параметры webhook, опроса и доступа уточняются после выбора источника.

## Граница прототипа

Достаточно работающего интерактивного сервиса с расчетом одного дня. Площадка размещения не является критерием. Перерывы, другие часовые пояса и подробный показ влияния новой заявки относятся к дополнительным возможностям.
